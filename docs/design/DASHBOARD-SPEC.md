# 小胰宝工作台 · 全局看板规格

日期：2026-10-13 · 状态：**设计建议稿，供用户讨论；非已实现界面**。

上级文档：[SPEC-v0.4.md](./SPEC-v0.4.md) §3。本文只定义**看板**：它看什么、每格怎么算、状态怎么分、缺数据怎么办、长什么样。

---

## 1. 看板要回答的问题

看板是一屏掌握病人综合状态的大屏。它服务于三个真实场景：

1. **家属每天扫一眼**：最近有没有需要处理的事？状态跟上次比是稳的还是在变？
2. **问诊前 5 分钟准备**：医生会问的几件事（体能、治疗到哪一步、有没有可试的临床）能不能立刻答上来。
3. **换医生/换医院/家属交接**：把病人情况一次讲清楚，不用翻一摞报告。

因此看板的设计取向是**快速定位 + 可下钻取证**，不是数据分析工具，也不是风险预警系统。

### 1.1 三条硬设计原则

**原则一：看板只呈现「有依据的状态」，不做医学判断。**

- 可以显示：ECOG 2 分、已完成二线治疗、白蛋白低于参考范围、BMI 17.8。
- 不可以显示：病情进展、预后不良、建议换方案、风险高危。

只有医生能下结论。看板做的是**把事实摆整齐、把缺口标出来**。

**原则二：缺口必须显式，绝不能默认为正常。**

这是最容易出错的地方。没有做营养评估，看板必须显示「未评估」，不能显示绿色正常。默认为正常会让家属以为「这块没问题」，而实际上只是没人看过。

**原则三：红绿灯要用来指路，不是用来吓人。**

用户要求使用红绿灯指标（红=警示、黄=关注、绿=良好），这是好习惯，也符合直觉。但有一个必须守住的边界：

> **绿色只能表示「已记录的数据未见异常」，绝不能表示「病人健康」。**

因为看板的数据永远是不完整的。如果某维度没数据却给绿色，用户会以为「这块没事」。所以绿灯必须配数据依据，无数据一律走灰色虚线（未评估）。

同理，**红色只用于「已确认的客观异常指标」**，不用于工作台自己推断的风险等级。例如：

- ✅ 红灯：总胆红素 3.2 mg/dL（参考范围 0.3–1.2）
- ❌ 红灯：「胆道梗阻高危」（这是工作台在替医生下判断）

### 1.2 状态分级：五级红绿灯

在用户要求的红黄绿基础上，补充两个必要级别（无数据、冲突），形成五级。8 个维度共用：

| 级别 | 语义 | 色值 | 圆点/边 | 什么时候用 |
|---|---|---|---|---|
| `good` | **良好** | 绿 `#2E7D5B` / 底 `#E8F5EE` | 实心绿点 | 有数据，指标在参考范围内，或状态为「无/已完成/稳定」 |
| `watch` | **关注** | 黄 `#B8860B` / 底 `#FFF6DC` | 实心黄点 | 有数据，但存在需要留意的情况（轻度异常、接近临界、待复核） |
| `alert` | **警示** | 红 `#C0392B` / 底 `#FCEBE8` | 实心红点 | 有数据，且存在**明确的客观异常**（指标远超参考范围、活动性并发症） |
| `unknown` | **未评估** | 灰 `#7C8C84` / 白底 | 虚线边框 | 没有任何数据，或数据不足以判断 |
| `conflict` | **记录冲突** | 紫 `#655472` / 底 `#F1F0F6` | 实心紫点 | 同一事实有矛盾记录，系统不替用户选 |

**分级判定必须可回溯到客观依据**。每张卡点开都要能看到：依据哪个值、参考范围是多少、记录日期、来源资料。没有依据就不许给颜色。

**`alert` 的文案规则**：显示客观事实，不显示结论。

| 禁止 | 使用 |
|---|---|
| 病情进展 / 恶化 | 总胆红素 3.2 mg/dL 高于参考范围 0.3–1.2 |
| 高危 / 危险 | 存在活动性记录：胆道梗阻（2026-10-08） |
| 需立即处理 | 建议与医生确认当前情况 |

`alert` 卡片底部固定一行提示「建议与医生确认」，**不提供任何处理建议**。

**`unknown` 是一等公民**。看板的「资料完整度」统计各维度 `unknown` 比例，帮用户知道还差什么。灰色虚线在视觉上必须与绿色实底明显区分，避免被误读成「没问题」。

## 2. 8 个维度

用户列出的 8 个维度全上。每个维度定义：看什么、口径、分级规则、数据来源、缺口时显示什么。

### 2.1 基本体能

| 项 | 定义 |
|---|---|
| **看什么** | ECOG 评分（或 KPS）、体重变化趋势、活动能力描述 |
| **口径** | 取最近一次已确认的 ECOG 记录；体重取最近两次已确认记录计算变化率与时间跨度 |
| **分级** | `good`：ECOG 0–1 且体重稳定；`watch`：ECOG 2，或非计划体重下降 ≥5%/1 个月或 ≥10%/6 个月；`alert`：ECOG 3–4；`unknown`：无 ECOG 记录 |
| **来源** | 手工录入或从病历文本提取（`ClinicalFact`）；体重来自 `Observation` |
| **缺口显示** | 「未记录体能状态」+「补录 ECOG」入口 |
| **注意** | ECOG 3–4 标 `alert`，提示「建议与医生确认当前治疗耐受性」；工作台不给出「不适合治疗」结论。红色指 ECOG 数值本身，不是工作台判定的风险 |

### 2.2 治疗情况与治疗线数汇总

| 项 | 定义 |
|---|---|
| **看什么** | 当前治疗方案、已完成线数、最近一次治疗日期、下一周期时间 |
| **口径** | 来自 `TreatmentLine` 集合；「当前方案」= 起止日期覆盖今天且未标终止的记录；线数 = 已完成线数 + 当前线 |
| **分级** | `good`：有当前方案且终止原因非进展；`watch`：最近一次终止原因为「疾病进展」或「毒性不耐受」；`alert`：无当前方案且无后续计划记录；`unknown`：无任何治疗记录 |
| **来源** | `TreatmentLine`（与病情整理共用，见 SPEC-v0.4 §4.2） |
| **缺口显示** | 「未记录治疗经过」+「补充治疗记录」入口 |
| **注意** | 这是匹配分析的直接输入。线数错误会直接导致匹配结论错误，因此看板上线数旁提供「核对治疗线数」入口 |

### 2.3 可匹配临床

| 项 | 定义 |
|---|---|
| **看什么** | 已完成匹配分析的试验中，三档各自的数量 |
| **口径** | 取该患者最近一次匹配分析的结果集；「可能冲突 0 项」的试验计入「无已知冲突」；未做匹配的试验不计入 |
| **分级** | `good`：存在至少一个「无已知冲突」的试验；`watch`：所有已分析试验都至少有一条可能冲突；`unknown`：未做过匹配分析或档案不完整 |
| **来源** | `MatchAssessment` + `TrialEligibilityRule` |
| **缺口显示** | 「尚未进行匹配分析」+「开始匹配」入口 |
| **注意** | 文案严格使用「无已知冲突」，**禁止**写「符合入组」「推荐」「适合」。看板不显示试验名称排名，避免被当成推荐 |

### 2.4 营养评估

| 项 | 定义 |
|---|---|
| **看什么** | BMI、体重变化、能量摄入与目标差值 |
| **口径** | BMI 来自最近一次已确认身高体重；能量建议由用户或医生设定的目标值给出，实际摄入来自记录 |
| **分级** | `good`：BMI 18.5–24 且体重稳定；`watch`：BMI 18.5–20 或 24–28，或体重下降达 §2.1 阈值；`alert`：BMI < 18.5 或 ≥ 28；`unknown`：无身高体重记录 |
| **来源** | `NutritionAssessment`（二期界面，一期预留）；体重来自 `Observation` |
| **缺口显示** | 「未评估营养状态」+ 说明二期开放 |
| **注意** | 不给出具体营养处方。能量建议只呈现「记录的目标」与「实际」的差距，不给补充剂推荐 |

### 2.5 心理评估

| 项 | 定义 |
|---|---|
| **看什么** | 最近一次情绪量表结果与分级、是否需要支持 |
| **口径** | 由用户或专业人员使用约定量表（如 GAD-7、PHQ-9）记录，工作台只呈现得分与既定分级，不自行解释 |
| **分级** | 按所用量表的官方分界映射到 `good` / `watch` / `alert`；未做评估为 `unknown` |
| **来源** | `PsychAssessment`（二期界面，一期预留） |
| **缺口显示** | 「未做过情绪评估」+ 说明二期开放 |
| **注意** | 工作台不做心理诊断；若用户主动记录「需帮助」，显示本地/社区支持资源入口，不做危机干预承诺 |

### 2.6 并发症评估

| 项 | 定义 |
|---|---|
| **看什么** | 主要并发症风险提示：消化道出血、胆道梗阻、肠梗阻、感染 |
| **口径** | 每个并发症取 `ComorbidityStatus` 的状态（活动/既往/无/未知）+ 与之相关的客观指标（如胆红素、CA19-9、体温、白细胞） |
| **分级** | `good`：状态为「无」或有客观依据显示稳定；`watch`：状态为「既往」，或相关指标轻度超出参考范围；`alert`：状态为「活动」且相关指标明显异常；`conflict`：记录冲突；`unknown`：未记录 |
| **来源** | `ComorbidityStatus` + `Observation` |
| **缺口显示** | 「未记录并发症状态」+「补充记录」入口 |
| **注意** | **工作台不计算风险概率、不输出风险评分。**「风险提示」的真实含义是「这个人有相关记录或异常指标，值得留意」，而不是工作台预测了风险。文案必须写清依据，例如「胆红素 3.2 mg/dL 高于参考范围（记录于 2026-10-08）」，而不是「胆道梗阻风险高」 |

### 2.7 毒性管理

| 项 | 定义 |
|---|---|
| **看什么** | 当前活动性毒性的类型与分级（CIPN、皮疹、恶心呕吐、骨髓抑制等） |
| **口径** | 取 `ToxicityRecord` 中未标转归的记录，按 CTCAE 分级呈现 |
| **分级** | `good`：无活动性记录或均为 1 级；`watch`：存在 2 级；`alert`：存在 ≥3 级；`unknown`：未记录 |
| **来源** | `ToxicityRecord`（二期界面，一期预留） |
| **缺口显示** | 「未记录治疗相关不良反应」+ 说明二期开放 |
| **注意** | 分级用 CTCAE 标准表述，工作台不改写为通俗结论；≥3 级时提示「建议尽快联系医生」而非自行处理建议 |

### 2.8 总体关注项

不是第 8 个独立数据维度，而是**跨维度的聚合视图**：把所有 `watch` / `alert` / `conflict` 项按时间与紧急程度列出。

**布局上的体现**：它是看板左侧最大的区块，不以宫格卡片形式出现，而是列表。因此看板是「1 个聚合区块 + 7 张维度卡」，合计覆盖 8 个维度。这一分工必须与原型和验收口径一致。

| 项 | 定义 |
|---|---|
| **看什么** | 当前所有需关注项的统一列表 |
| **口径** | 汇总 §2.1–2.7 中所有 `watch` / `alert` / `conflict` 级别的具体条目，附各自依据与来源 |
| **排序** | 用户手动置顶 > 有客观指标依据 > 其他；同组内按记录日期倒序 |
| **分级** | 不适用（本身是聚合） |
| **来源** | 上述各维度 |
| **缺口显示** | 「暂无需关注项」+ 同时说明「这不代表病情稳定，仅表示已记录内容中没有需关注项」 |
| **注意** | 这条免责说明不可省略。空列表不等于健康，只等于没有记录到问题 |

## 3. 布局

### 3.1 分层信息架构（v2，替代宫格卡片）

**v1 的问题**（实测截图确认）：7 张宫格卡片高度不齐、右列留白、末张孤立成行；每张卡重复一个「查看详情」链接；6 种色块同时出现导致视觉无处落点。

**v2 改为三层，逐层展开**：

| 层 | 内容 | 交互 |
|---|---|---|
| **第 1 层：概要条** | 患者身份 + **一句话结论**（如「2 项警示」）+ 资料完整度 | 静态，一眼看到重点 |
| **第 2 层：需关注项** | 跨维度汇总，一行一条：状态点 + 结论 + 依据 + 来源 | 静态，附来源 |
| **第 3 层：维度状态** | 7 行列表：状态点 + 名称 + 主值 + 级别 + 折角 | **点击展开**依据与两个动作 |
| **第 4 层：全程管理** | 4 项横排，状态点 + 名称 + 数据状态 | 点击进入子页 |

### 3.1.1 对齐规则（必须一致）

用户明确指出「要素没有对齐，对称混乱」。硬规则：

| 列 | 对齐 | 宽度 |
|---|---|---|
| 状态点 | 固定左缘 | 8px |
| 名称 | 固定列 | 108px |
| 主值 | 左对齐，可伸缩 | 1fr |
| 级别文字 | **右对齐，固定列** | 62px |
| 折角图标 | 固定右缘 | 18px |

所有维度行共用同一 `grid-template-columns`，因此**每行的每一列都严格对齐**。实测断言：7 行的左缘坐标相同、级别列右缘坐标相同。

关注项行同理：状态点 / 主内容 / 来源三列，来源列右对齐固定最大宽 190px。

### 3.1.2 标题与序号规则

用户明确否定了大号圆点序号（「09）」这类）。规则：

| 层级 | 呈现 |
|---|---|
| 一级 Tab | 序号 `1`–`7`，等宽小字，位于文字前，颜色浅灰；激活时随文字变深 |
| 区块标题（看板内） | **不加任何序号**。仅用 15px / 640 字重的小标题 + 一行浅灰副说明 |
| 页面主标题（各模块页） | 不加序号 |

**序号只保留在一级 Tab**，用于口头指代导航位置。看板内部的 section 标题不加数字，因为：

1. 大号数字（`01` `02`）视觉重量过大，会与内容争抢注意力。
2. 看板只有三个 section，用户不需要靠编号定位。
3. 「09）」这类写法数字与括号混排，本身不够整洁。

### 3.1.3 降噪规则

| 规则 | 说明 |
|---|---|
| **减色** | 卡片不再整块着色。颜色只出现在 **8px 状态点**和级别文字上。全屏着色面积 <2% |
| **去重复** | 删除每张卡重复的「查看详情 →」。动作只在展开层出现，且只有两个 |
| **去装饰** | 不使用「01 / 02」圆点序号、不使用卡片标题前的装饰点 |
| **线条最少** | 用 `1px` 分隔线代替卡片边框；一个 section 只有一个外框 |
| **层级靠留白与字重**，不靠框和底色 |

### 3.1.4 折叠与分层点击

- 默认**全部收起**。理由：7 个维度同时展开会立刻回到 v1 的信息过载。
- 同时**只允许一个展开**（手风琴）。点击已展开项则收起。
- 展开层内含**依据说明 + 两个动作**：查看来源与记录 / 补充资料。
- 折叠按钮带 `aria-expanded`，可用键盘操作。
- 折角图标旋转有过渡（`transform .18s cubic-bezier(.16,1,.3,1)`），符合动效层 `MOTION_INTENSITY: 2`（仅 hover/active/展开过渡，无自动动画）。

### 3.2 中等布局（760 ≤ W < 1080px）

需关注项占满宽度；维度行保持单列（不折两列，避免打断纵向扫读节奏）。

### 3.3 窄布局（W < 760px）

- 全程管理 4 项折为 **2×2**，去掉中间分隔线。
- 维度行改为两行式：状态点 + 名称 + 级别在第一行，主值 + 折角在第二行。仍保持左缘对齐。
- 需关注项的**来源列隐藏**（宽度不足），依据文字保留。
- 展开层左内边距与其他行对齐（缩到 20px）。

### 3.4 状态与交互

| 交互 | 行为 |
|---|---|
| **点维度行** | **展开/收起该行依据**（第一层，不跳页） |
| 点展开层「查看来源与记录」 | 跳转到该维度的详情页 |
| 点展开层「补充资料」 | 打开该维度的补录入口 |
| 悬停维度行 | 背景轻微加深（`#F7FAF9`）；`:active` 下沉 1px |
| 悬停级别文字 | 显示口径说明（如「警示 = 已有客观指标明确超出参考范围，建议与医生确认」） |
| 点需关注项 | 展开该条的完整依据：值、参考范围、记录日期、来源资料、跳转原文 |
| 「资料完整度」 | 点开显示各维度是否有数据，缺什么 |

**注意**：v1 的「点维度卡直接跳页」已废弃。直接跳页会让用户失去看板上下文；改为先展开、再决定是否深入。

## 4. 数据来源与刷新

| 维度 | 主要来源实体 | 刷新时机 |
|---|---|---|
| 基本体能 | `ClinicalFact`（ECOG）+ `Observation`（体重） | 核对确认后 |
| 治疗情况 | `TreatmentLine` | 治疗记录变更后 |
| 可匹配临床 | `MatchAssessment` | 匹配分析完成后 |
| 营养 | `NutritionAssessment` + `Observation` | 二期；体重确认后 |
| 心理 | `PsychAssessment` | 二期 |
| 并发症 | `ComorbidityStatus` + `Observation` | 记录变更后 |
| 毒性 | `ToxicityRecord` | 二期 |
| 总体关注项 | 上述聚合 | 任一变化后 |

看板不缓存独立副本用于显示，读取时按当前数据实时计算分级；`DashboardSnapshot` 只用于解释历史与对比，不用于渲染当前状态。

### 4.1 档案变更后的行为

- 治疗线数、基因、并发症变更后，看板的「可匹配临床」标「档案已更新，建议重新评估」，不自动重算。
- 理由：匹配结论会直接影响用户对试验的判断，静默重算会让用户以为结论一直如此，无法追溯。

### 4.2 数据版本与时间显示

- 顶栏显示「资料更新至 YYYY-MM-DD」，取最近一次确认记录的时间。
- 每个维度内显示该维度自己的数据日期，不共用一个时间戳。
- 日期未知显示「日期未记录」，不省略。

## 5. 空状态与边界情况

| 情况 | 看板表现 |
|---|---|
| 无患者 | 两入口：建立患者档案 / 先浏览试验资料。不显示空的 8 宫格 |
| 有患者但无任何资料 | 8 维度全部 `unknown`；顶部说明「还没有录入资料，可以从导入病历开始」 |
| 只有部分资料 | 各自独立：有数据的显示状态，无数据的显示 `unknown`；完整度如实计数 |
| 资料位置不可用（外置盘未挂载） | 顶部横幅说明位置不可用，各维度显示「资料暂不可读」，不显示为无数据 |
| 数据冲突 | 该维度用 `conflict` 级别，点开显示两条冲突记录及来源，要求用户确认 |
| 未做匹配分析 | 「可匹配临床」显示 `unknown` + 「开始匹配」入口，不显示 0 个 |

## 6. 文案规范

看板上所有文案受此约束。这是医疗场景，措辞会直接影响用户决策。

| 禁止 | 使用 | 原因 |
|---|---|---|
| 病情进展 / 恶化 | 记录值的变化（如「CA19-9 从 82 升至 148」） | 工作台不能判断进展 |
| 风险高 / 高危 | 「有相关记录 / 指标超出参考范围」 | 工作台不计算风险 |
| 符合入组 / 适合 / 推荐 | 「无已知冲突」 | 入组判断属于医生与研究中心 |
| 需要治疗 / 建议换方案 | 「当前方案记录于…」 | 不给医疗建议 |
| 正常 / 健康 | 「未见超出参考范围的已确认记录」 | 避免把「数据齐」说成「健康」 |
| 危险 / 危急 / 立即就医 | 「建议与医生确认」 | 工作台不做急症判断 |
| （空） | 「未评估」 | 缺口必须显式 |

### 6.1 红绿灯的文案配套

用户要求红绿灯，颜色本身**不携带结论**，必须由文字说出依据。规则：

| 级别 | 颜色 | 必须显示的文字 |
|---|---|---|
| 良好 | 绿 | 依据值 + 「未见异常」或状态描述 |
| 关注 | 黄 | 依据值 + 「需关注」或具体异常描述 |
| 警示 | 红 | 依据值 + 参考范围 + 「建议与医生确认」 |
| 未评估 | 灰虚线 | 「未评估」+ 补录入口 |
| 冲突 | 紫 | 「记录冲突」+ 两条冲突记录 |

**禁止只有颜色没有文字**。色盲用户、黑白打印、以及「红=警告」的直觉误读，都要求文字独立传达完整信息。

**禁止在同一个区块混用颜色语义**。红色在这一屏只表示「客观指标异常」，不能又表示「未读」「错误」「删除」等其他含义（这是前端常见的颜色语义冲突）。

## 8. v3 首页周期计划与阅读顺序

首页按患者当下最容易执行的顺序组织：现在可以做 → 周期计划（化疗、血液检查、肿瘤标志物、增强 CT）→ 未来两周 → 当前变化提醒（8 个维度）→ 资料概况、持续记录与家庭协作。

周期卡中心显示当前周期或次数，外环只表示距离下次计划事项的时间进度。点击后显示该主题的最近记录、资料来源与下次计划：化疗显示方案、周期与治疗后记录；血液检查显示最近确认数值；肿瘤标志物显示最近两次同指标的日期、单位和变化值；增强 CT 显示原文核对状态及部位、数量、尺寸、比较日期等待核对项。

数值或影像变化只能显示为「变化提示」或「待核对」。看板不得根据 CA19-9、CEA、CT 或其组合写出进展预警、疗效判断或治疗建议。

## 9. 首页未来两周日历与事件操作

看板在周期计划后提供一个从今天起 14 天的日历模块。用户点选日期查看当天待办，并可从首页直接添加、编辑、完成或取消事件；日期默认采用所选日。具体状态、数据范围和验收项见 [CALENDAR-SPEC.md](./CALENDAR-SPEC.md)。

该模块复用既有预约数据表，不复制一份首页日历数据。日历只显示用户记录的计划；化疗、血常规、肿瘤标志物和 CT 的时间由用户根据医疗团队确认后维护。更改计划须通过显式编辑表单，避免拖拽误触。日历空态也保留「添加事件」入口。
