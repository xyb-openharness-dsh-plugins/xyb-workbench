# 小胰宝工作台 · 数据流与自动更新规格

日期：2026-10-13 · 状态：**设计建议稿。回答「用户录入后看板会不会自动更新、处理逻辑是什么」。**

上级文档：[SPEC-v0.4.md](./SPEC-v0.4.md)（数据模型） · [DASHBOARD-SPEC.md](./DASHBOARD-SPEC.md)（看板） · [CARE-MANAGEMENT-SPEC.md](./CARE-MANAGEMENT-SPEC.md)（全程管理）。

---

## 1. 直接回答

**会更新，但不是「推送」式的更新，而是「读取时实时计算」。**

这是本文最重要的一句话。工作台**没有**「录入后触发看板刷新」这个动作，因为看板**不保存自己的副本**。用户录入一条 Port 维护记录，看板下次渲染时自然就变了——中间没有任何同步步骤。

[DASHBOARD-SPEC §4](./DASHBOARD-SPEC.md) 已明确：

> 看板不缓存独立副本用于显示，读取时按当前数据实时计算分级；`DashboardSnapshot` 只用于解释历史与对比，不用于渲染当前状态。

这个设计的好处是**不会出现「看板说 A、详情页说 B」的不一致**——因为只有一个数据来源。

## 2. 处理链路（以 Port 维护记录为例）

```text
① 用户录入
   在「血管通路管理」填维护记录（日期、操作、执行人、异常）
        ↓
② 写入单一实体
   CatheterRecord 新增一条 maintenance 子记录
   （Port 与 PICC、带管共用 CatheterRecord，见 §4）
        ↓
③ 不触发任何"同步"
   没有后台任务、没有刷新标记、没有缓存失效逻辑
        ↓
④ 下次渲染时实时计算
   全程管理卡片：读 CatheterRecord → 算「距上次维护 N 天」
   看板：按 §5 的规则决定是否体现在某个维度
        ↓
⑤ 界面说明数据时间
   该卡片显示自己的数据日期，不共用时间戳
```

**关键：②和④之间没有③。** 这是刻意的——少一层同步就少一类不一致缺陷。

## 3. 三类数据的更新语义（必须区分）

不是所有东西都「实时」。按对用户决策的影响分三档：

| 类型 | 例子 | 更新方式 | 理由 |
|---|---|---|---|
| **事实型** | 维护记录、体重、化验值、置管日期 | **实时计算** | 客观数据，变了就是变了，不需要用户确认 |
| **派生型** | 「距上次维护 12 天」、BMI、指标趋势线 | **实时计算** | 从事实型推导，不单独存储 |
| **结论型** | 临床匹配结果、看板分级、总体关注项 | **提示但不自动重算** | 见 §4 |

**结论型为什么要例外**：[DASHBOARD-SPEC §4.1](./DASHBOARD-SPEC.md) 已给出理由——

> 治疗线数、基因、并发症变更后，看板的「可匹配临床」标「档案已更新，建议重新评估」，**不自动重算**。理由：匹配结论会直接影响用户对试验的判断，静默重算会让用户以为结论一直如此，无法追溯。

这条原则要推广到**所有会改变结论的录入**，不止匹配：

| 录入内容 | 看板行为 |
|---|---|
| Port 维护记录 | ✅ 实时更新（事实型派生，不影响结论） |
| 新化验值 | ✅ 实时更新（趋势线、异常提示） |
| 新并发症状态 | ⚠️ 标「档案已更新，建议重新评估」，不自动改匹配结论 |
| 治疗线变更 | ⚠️ 同上 |
| 基因结果变更 | ⚠️ 同上 |

**判断规则**：这条录入会不会改变「我们建议你做什么」？会 → 提示不重算；不会 → 实时。

## 4. 实体归属：Port 记录存在哪

现状有**一处不一致需要修正**。

[SPEC-v0.4 §6.1](./SPEC-v0.4.md) 定义：

| 实体 | 字段 |
|---|---|
| `CatheterRecord` | `catheterId`、`patientId`、类型（**PTCD/手术置管/Port/PICC**）、置入日期、位置、状态、并发症、维护记录 |

**Port 与 PTCD 共用 `CatheterRecord`，用「类型」字段区分。** 这是对的，理由：

| 理由 | 说明 |
|---|---|
| 字段高度重合 | 两者都有置入日期、位置、状态、维护记录 |
| 生命周期相同 | 置入 → 维护 → 移除 |
| 避免重复实体 | 建两个实体会有大量重复逻辑 |

但**规格间存在矛盾，须修正**：

| 文档 | 说法 | 冲突 |
|---|---|---|
| [SPEC-v0.4](./SPEC-v0.4.md) 第 313 行 | `CatheterRecord` **一期预留** | ⚠️ |
| [CARE-MANAGEMENT-SPEC §3.3/3.4](./CARE-MANAGEMENT-SPEC.md) | 设计了带管/血管通路的一期界面与卡片 | ⚠️ |

**建议**：`CatheterRecord` 从「一期预留」改为**一期实现**。理由：

1. 全程管理是七个一级 Tab 之一，一期就要可见
2. 用户档案里**已经有置管数据**（如 Port 置入信息），不实现就没有存放处
3. 数据结构简单（一条记录 + 维护子记录），实现成本低

**配套要加 `maintenance` 子结构**（当前只在字段名里提到，未展开）：

```text
CatheterRecord
  ├─ catheterId, patientId
  ├─ type: PTCD | 手术置管 | Port | PICC
  ├─ implantDate, site, status
  ├─ device: { brand, model }        ← 新增：器械型号（如 法国布朗 BL2012）
  ├─ operator: { hospital, doctor }  ← 新增：置入医院与医生
  ├─ complications: [...]
  └─ maintenances: [                 ← 展开为子记录，而非一个字符串
       { date, action, performer, note, abnormal }
     ]
```

**`maintenances` 必须是数组**，理由：维护是**周期性重复事件**。「距上次维护 N 天」要取最近一条；维护历史要能看趋势（是否越来越频繁）。存成单个字符串字段做不到这两点。

## 5. Port 维护记录影响哪些界面

录一条维护记录后，按当前设计**只有一处会变**：

| 界面 | 是否变化 | 说明 |
|---|---|---|
| 血管通路管理卡片 | ✅ 变 | 「距上次维护 N 天」、最近维护日期 |
| 看板的全程管理缩略块 | ✅ 变 | 卡片内的状态 |
| **看板 8 个维度** | ❌ **不变** | 见下 |

**这里有个设计缺口**：[DASHBOARD-SPEC §2](./DASHBOARD-SPEC.md) 的 8 个维度是——基本体能、治疗情况、可匹配临床、营养、心理、并发症、毒性、总体关注项。

**没有「带管/血管通路」维度**，但 [DASHBOARD-SPEC 第 211 行] 的示意图里画了这四个块。

两种处理，**建议选 A**：

| 方案 | 做法 | 理由 |
|---|---|---|
| **A（建议）** | 带管/通路**不进 8 维度**，只作为「总体关注项」的一个信号源 | 8 维度是「影响治疗决策」的维度；管路维护是**操作性事务**，不是病情维度 |
| B | 扩到 10 维度 | 会稀释看板焦点；且维护周期正常时无信息量 |

**但方案 A 需要补一条规则**（当前缺失）：

```text
管路/通路异常 → 汇入「总体关注项」，并汇入「并发症」维度
触发条件（任一）：
  · 维护记录标了 abnormal
  · 距上次维护超过该类型推荐周期（Port 约 4 周，PICC 约 1 周，PTCD 按医嘱）
  · 有管路相关并发症记录（感染/堵塞/血栓）
```

**注意**：超期只做**中性提示**，不做压力性告警。这与 [CARE-MANAGEMENT-SPEC §3.3](./CARE-MANAGEMENT-SPEC.md) 的约束一致——「只显示『距上次维护 X 天』的中性事实，不做自动提醒推送」。

## 6. 跨模块联动（谁引用谁）

```text
CatheterRecord（含 maintenance）
    │
    ├─► 全程管理卡片        「距上次维护 N 天」
    │
    ├─► 并发症管理          管路相关感染/堵塞 → ComorbidityStatus
    │
    ├─► 毒性管理            静脉炎、血栓 → ToxicityRecord
    │
    └─► 看板总体关注项       异常/超期时汇入

营养管理 ──► 看板营养维度 + 一图秀体重曲线
心理支持 ──► 看板心理维度（不用红绿灯）
```

**联动原则**（与 [CARE-MANAGEMENT-SPEC §4](./CARE-MANAGEMENT-SPEC.md) 一致）：**同一份数据被多处引用，不复制**。例如管路感染既是 `CatheterRecord.complications` 也是 `ComorbidityStatus`——但**必须只存一份**，另一处通过引用关联，否则两边会不一致。

**建议实现**：`ComorbidityStatus` 里存 `sourceRef: { entity: 'CatheterRecord', id }`，指向来源。展示时读来源，不冗余存副本。

## 7. 用户可感知的行为（界面文案）

用户问的其实是「我填了以后会发生什么」。界面要**明确告知**，不猜：

| 场景 | 界面文案 |
|---|---|
| 保存维护记录后 | 「已记录。全程管理卡片与看板已更新。」（如涉及结论则加：「看板的临床匹配标注为『建议重新评估』」） |
| 维护超期 | 「距上次维护 42 天（Port 建议约 4 周维护一次）」——**陈述事实 + 参考周期**，不说「危险」 |
| 录入改变了匹配结论相关数据 | 「档案已更新，建议重新评估临床匹配」+ 跳转按钮 |
| 看板数据时间 | 顶栏「资料更新至 YYYY-MM-DD」；维度内各自标日期 |

**最后一条要强调**：看板顶栏的时间是**最近一次确认记录**的时间，不是「看板刷新时间」。因为不存在刷新——只有数据变化。

## 8. 离线/失败情况

| 情况 | 行为 |
|---|---|
| 保存时网络中断 | 明确报错，**不假装成功**；数据不丢（本地优先，见 [STORAGE-SPEC](./STORAGE-SPEC.md)） |
| 保存成功但渲染失败 | 下次进入重新读取；不缓存半成品 |
| 多个界面同时打开 | 读取时实时计算 → 天然一致，无需处理冲突 |
| 数据被外部改动（如 CLI） | 下次读取即反映，无缓存需要失效 |

**「无缓存」的直接收益**：不需要缓存失效逻辑，也就不存在「缓存过期导致显示旧值」这类缺陷。
