## 2. 本次会话（2026-10-13）完成事项

### 2.1 全程管理四主题图标

[prototype-v2.html](./prototype-v2.html) 的四个主题各加扁平化线性图标（24×24 内联 SVG，`currentColor` + `stroke-width: 1.6`）：

| 主题 | 造型 | 状态色（演示数据） |
|---|---|---|
| 毒性管理 | 盾牌 + 惊叹点 | 金 `#B8860B` |
| 并发症管理 | 心电波形 + 警示点 | 红 `#C0392B` |
| 带管管理 | 管道 + 引流口 | 灰 `#9AA9A2` |
| 血管通路管理 | 血管通道 + 端口 | 灰 `#9AA9A2` |

**设计取舍**：图标**取代**了原来的状态点——状态点与右侧文字标签本就重复表达同一件事，图标同时承担「识别主题」与「指示状态」两个职责，信息密度更高。

**不用 emoji、不用字体图标**：emoji 跨系统渲染差异大，字体图标需外部依赖，内联 SVG 保持单文件离线可用。

**修了一个缺陷**：详情页最初把图标颜色写死成灰色，未带 `lv-*` 类，导致点进「并发症管理」时图标变灰、与列表上的红色不一致。改为通过父容器类 + `currentColor` 传递后修复。

**待定项**：当前只有灰/金/红三档，**没有「良好绿」**——「有数据且正常」时图标也是灰的。演示数据里四项恰好没有 good 状态，未暴露。倾向保持现状（只有需要关注时才变色），若用户要「正常显示绿色」需明确。

### 2.2 输液港模拟数据 + 一图秀线色同源

用户要求加输液港数据（法国布朗 BL2012，复旦肿瘤医院许立超医生，2025-01-20），并要求一图秀的线色与指标图标一致。

2. **`.tl-swatch` 选择器歧义**——该 class 被两处复用：图表图例（用 inline `background`）与用药时间轴色块（用 CSS class）。我的测试断言选到了后者，误报「图例色块为空」。**图表颜色本来是对的，是测试选择器写错了**。已把用药色块改名为 `tl-medblock`。修正后 29/30 通过（唯一「失败」是断言阈值写错：默认视图只选 2 个指标，所以只有 2 个图例色块，属正常行为）。

**线色同源实现**：一图秀的线色改用与指标目录相同的稳定哈希分配，保证同一指标在任何界面颜色一致。

### 2.3 新建 [DATA-FLOW-SPEC.md](./DATA-FLOW-SPEC.md)

回答用户「未来录入 Port 维护记录，会自动更新到看板吗」。

**核心答案**：**会更新，但不是「推送」式，而是「读取时实时计算」**。工作台**没有**「录入后触发看板刷新」这个动作，因为看板**不保存自己的副本**（`DASHBOARD-SPEC.md` 已定此原则）。好处是不会出现「看板说 A、详情页说 B」。

**三类数据的更新语义必须区分**：

| 类型 | 例子 | 更新方式 |
|---|---|---|
| 事实型 / 派生型 | 维护记录、化验值、「距上次维护 N 天」 | **实时计算** |
| 结论型 | 匹配结果、看板分级 | **提示但不自动重算** |

判断规则：**这条录入会不会改变「我们建议你做什么」**？会 → 提示不重算；不会 → 实时。原则从「匹配」推广到所有改变结论的录入。

**发现两处规格不一致**（待用户确认）：

| 问题 | 现状 | 建议 |
|---|---|---|
| `CatheterRecord` 一期状态 | `SPEC-v0.4.md:313` 写「一期预留」 | 改为**一期实现**（全程管理是一级 Tab、用户档案已有置管数据、结构简单） |
| 带管/通路是否进看板 8 维度 | `DASHBOARD-SPEC.md:211` 示意图画了四个块，但 §2 的 8 维度不含它们 | **不进 8 维度**，只作「总体关注项」信号源（管路维护是操作性事务，非病情维度） |

### 2.4 新建 [SCHEMA-SPEC.md](./SCHEMA-SPEC.md)

回答用户「SQLite 是否需要设计 schema 配合各 Tab 与指标」。

**结论：需要，而且现在还没有**——34 个实体（v0.3 的 15 + v0.4 新增 19）全部是散文描述，无表、无类型、无主外键、无索引、无约束。

**用户指出一处设计原则错误，已修正**：初稿写「schema 由 Tab 反推」，用户质疑「Tab 变了 schema 就要变吗？这违反 DB 设计原则」——**用户是对的**。Tab 恰是最易变的东西（本工作台一级 Tab 已 3 → 5 → 7 改过两轮），存储层被展示层绑架是典型反模式。

**修正后的正确关系**：

| 角色 | 地位 | 能否决定表结构 |
|---|---|---|
| **领域模型** | **权威** | ✅ 能 |
| **Tab / 界面** | **证据来源** | ❌ 不能 |
| 索引 | 由查询模式决定 | — |

Tab 的作用只有两个：**校验模型有没有漏**（某 Tab 要显示的东西模型里没有 → 模型漏了）、**推导索引**（索引本就是查询驱动的）。

**判断标准**：一个字段该不该进表，问「**它与界面无关地存在吗**」。已核查草案 DDL 本身是干净的（无 Tab 字面量、无页面状态列），是**措辞把因果讲反了**，已改五处。

**新增 §8「Schema 变更判断清单」**：一句话判据是「改变的是**数据是什么**还是**数据怎么看待**」，并给反面清单（出现 `display_order` / `is_expanded` / `color` / `tab_name` 即建模错误）。

**三个必须固化成约束的点**：

| 点 | 做法 |
|---|---|
| `>1000` 不是 1000 | 拆 `value_raw`（原文）+ `value_num`（可画图）+ `comparator` |
| 单位不一致不连线 | `unit_std_factor IS NULL` 的行在曲线上断线，变成可查询条件 |
| 未检测 ≠ 阴性 | `CHECK (status IN ('measured','not_tested','negative','unknown'))`，**不能用 NULL** |

**两个结构决策**：药物列表必须是子表（违反第一范式；且 `LIKE '%吉西他滨%'` 会误匹配「吉西他滨脂质体」，是**正确性缺陷**）；基因与病理共用一张表（领域同属「分子检测结果」，`assay_type` 是判别属性）。但 `Observation` 与 `GenomicAlteration` **建议不合并**（领域差异：指标有单位与参考范围、是同项重复测量；基因分型一次性确定且生命周期不同）。

## 4. 关键技术决策（含理由）

| 决策 | 理由 |
|---|---|
| **持久层用 `node:sqlite`，不用 `better-sqlite3`** | 本机实测可用（Electron 43 / Node 24.17 / SQLite 3.53 / WAL / FTS5 / JSON1 / 外键全通过）；零原生依赖，免去按平台打包 ABI 二进制 |
| **看板不缓存副本，读取时实时计算** | 结构上排除「两个页面两个数」；且无需缓存失效逻辑 |
| **结论变更时不静默重算** | 静默重算会让用户以为结论一直如此，无法追溯 |
| **统一用 `revision` 做失效传播** | 匹配评估记录生成时版本号，档案变更即标记 |
| **病历原件不进数据库** | 原件作为普通文件存 `documents/`，避免大字段入库 |
| **红绿灯五级（good/watch/alert/unknown/conflict）** | 用户要红黄绿，但「未检测」与「冲突」无法归入三档。**红色只表示已确认的客观指标异常**，不表示工作台推断的风险；绿色只表示已记录数据未见异常 |
| **颜色/形状/字号三重表达** | 色盲与灰度打印可辨识 |
| **心理维度不用红绿灯** | 全看板唯一例外——把情绪标红会造成二次伤害 |
| **一图秀单独占一级 Tab** | 看板是「一屏速览、不做医学判断」，一图秀是「全病程细看、时间对齐引导因果联想」，服务不同认知任务 |
| **MinerU 默认 pipeline 不用 vlm** | 官方明示 vlm 可能产生幻觉、pipeline 无幻觉。医疗场景「宁可漏，不可编」 |
| **MinerU 默认仅本地解析** | 云端服务会把病历传出，须明确告知、可关闭 |

**修过的真实缺陷（非测试问题）**：
