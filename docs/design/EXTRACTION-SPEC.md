# 小胰宝工作台 · 文档抽取与报告核对规格

日期：2026-10-13 · 状态：**设计建议稿。MinerU 部分已实测（见 §3）；表格重建与本地提取未实测**。

上级文档：[SPEC-v0.4.md](./SPEC-v0.4.md) · [RESOURCE-DEPENDENCIES.md](./RESOURCE-DEPENDENCIES.md) · [CASE-TEMPLATE-SPEC.md](./CASE-TEMPLATE-SPEC.md)。

本文回答两个问题：**抽取链路怎么搭**、**多份文件怎么核对**。

---

## 1. 抽取链路

### 1.1 五段式

```text
① 收录      文件进资料库（复制原件 + 计算 hash）
② 取文      数字版 PDF → 本地提取 ｜ 扫描件/图片 → MinerU
③ 结构      纯文本 → 区块识别 → 候选字段（规则 + 可选 AI）
④ 核对      人工逐字段确认（本文 §4 重点）
⑤ 入库      确认值进入正式数据（趋势/评估/匹配档案）
```

每段独立可失败、可重试。**②失败不阻断⑤**：用户可以直接手工录入。

### 1.2 取文段的分支判定

```text
文件类型？
├─ TXT / MD            → 直接读
├─ 数字版 PDF          → 本地文本提取
│   └─ 文本量 < 阈值 → 判为扫描件，转 MinerU
├─ 扫描件 PDF / 图片    → MinerU
├─ DOCX                → 本地解析（docx 是 zip+xml）
└─ 其他                → 提示不支持解析，仍可归档 + 手工录入
```

**判定阈值**：单页提取字符数 < 100 视为无文本层。实测样本中扫描件提取结果接近空。

### 1.3 为什么「先本地、后云端」

| 顺序 | 理由 |
|---|---|
| 本地优先 | 不联网、不上传、更快、无配额 |
| 云端兜底 | 只在本地确实拿不到文本时才用 |
| 用户确认 | 上传前必须告知（见 RESOURCE-DEPENDENCIES §2.6） |

## 2. 阶段②：MinerU 集成要点

（实测数据与限制见 [RESOURCE-DEPENDENCIES.md](./RESOURCE-DEPENDENCIES.md) §2）

### 2.1 三条硬约束与应对

| 约束 | 影响 | 应对 |
|---|---|---|
| 文件 ≤ 10 MB（flash） | 扫描件常超 | 走 precision；仍超则本地分页或降采样 |
| 页数 ≤ 20（flash） | 完整病历常超 | 同上 |
| 云端处理 | 病历隐私 | 明确告知 + 可关闭 |

### 2.2 输出处理

MinerU 输出 Markdown + HTML 表格 + 图片。三段处理：

| 处理 | 规则 |
|---|---|
| **表格重建** | MinerU 的 `full.md` 里表格是 `<table><tr><td>` 而非竖线表，必须先转成竖线表再谈对齐（见 §2.3） |
| 图片归档 | 内嵌图片存到 `derived/` 下，保留与原文的对应关系 |
| 原文保留 | Markdown 作为「解析文本」保存，**不覆盖原件**；核实时可对照原件或解析文本 |

### 2.3 表格重建（实测发现的关键点）

实测输出形如：

```html
<tr><td rowspan=1 colspan=1>2023/8/8- 2024/1/26</td><td rowspan=1 colspan=1>AG 方案8周期</td></tr>
```

实测结果：14 个 `<tr>`，每行 1–3 格，**结构可解析但有合并单元格**。

**这里最容易踩的坑**：MinerU 的 `full.md` 里表格是 HTML `<table><tr><td>`，**不是 markdown 竖线表**。
如果先做通用清洗（剥标签、压空白）再谈对齐，整张表会被压成一行，单元格之间失去边界——
而这条链路**不会报错**，只会把下一行的值读成上一行的结果，属于静默错读。

错误示范（剥完标签后再按行切）：

```
发生部位胃体肿瘤最大径6.8 cm核分裂象计数12 个/50 HPF切缘R0
```

正确做法是**先转竖线表，再做任何清洗**：

```
| 发生部位 | 胃体 |
| 肿瘤最大径 | 6.8 cm |
| 核分裂象计数 | 12 个/50 HPF |
```

重建规则（已实现，`dsh/extract.js` 的 `htmlTablesToPipes()`）：

1. **`colspan=n` 展开成 n 个单元格：第 1 格放值，其余 n−1 格补空占位。**
   **不能把值复制到它覆盖的所有位置。** 反例：病理竖表里 `<td colspan="2">胃体</td>`，
   复制会让「结果」列读成 `胃体`，把部位当成检验结果写进候选值。补空位后该格为空，抽取器自然跳过。
2. `rowspan` **当前未实现**（现有夹具里没有跨行合并）。遇到带 `rowspan>1` 的表，
   按行切分仍能保住行列边界，但纵向合并语义会丢失——需要时应先补实现再加夹具，
   不要在文档里假定它已被处理。
3. 单元格内的 `|` 替换成 `/`，否则会把竖线表切错列。
4. HTML 实体（`&lt;` `&gt;` `&amp;` `&nbsp;` 等）在输出单元格时还原，
   否则 `<0.5` 会变成字面 `&lt;0.5`，不等式解析不上。
5. 首行当表头，其后补一行 `| --- |` 分隔行。
6. 展开后按「表头行 + 数据行」识别；若表格无表头，标注「未识别到表头，请核对列含义」——不能猜。

**必须做重建**：原始 HTML 直接渲染会因合并单元格错位，用户无法核对。

**回归锁**：`test/extract.test.mjs` 里有一条反例测试，断言「剥标签后压成一行、抽出 0 条」。
它存在的意义是逼住顺序——将来若有人为了"简化"把转换挪到清洗之后，这条会先红。
凡是「先通用清洗、再结构化解析」的链路，都该有这样一条锁住顺序的反例测试。

## 3. 阶段③：字段抽取

### 3.1 区块识别（规则优先）

模版结构固定（见 CASE-TEMPLATE-SPEC §4.2），先用规则识别区块，再对区块内容抽取：

| 区块 | 锚点 |
|---|---|
| 基本情况 | `病情介绍` / `姓名` + `年龄` |
| 基因检测 | `基因检测` / `基因` |
| 病理免疫组化 | `病理` / `免疫组化` / `术后病理` |
| 既往治疗史 | `既往治疗史` / `治疗史` |

**规则优先于纯 AI**：结构稳定时规则更可预测、更便宜、更好调试。

### 3.2 候选值必带三样

| 必带 | 理由 |
|---|---|
| 原文片段 | 可对照核实；模版常有错字（`ARIDIA`、`丰都`），原文是唯一真相 |
| 页码/位置 | 能跳回原件定位 |
| 置信来源 | 区分「本地提取」「MinerU 解析」「AI 抽取」「手工输入」 |

## 4. 阶段④：报告核对（多文件）

**多文档 + 多页面 + 页内异构的完整设计见 [REVIEW-SPEC.md](./REVIEW-SPEC.md)。**

本节保留核对的基本原则；文档来源 list、页导航、页级内容类型分流、跨页比对等界面细节以 REVIEW-SPEC 为准。

用户问：「如果是多个文件，如何核对？」

### 4.1 问题分析

一次导入可能有 10+ 份文件（化验单、CT、病理、基因报告…）。朴素做法「一份一份核对」有三个问题：

| 问题 | 后果 |
|---|---|
| 不知道还剩多少 | 用户失去进度感，容易半途放弃 |
| 同类文件分散 | 三张化验单要来回切，无法横向比较 |
| 重复与冲突不可见 | 同一指标在不同报告里出现，无法发现 |

### 4.2 三种核对模式

提供三种模式，**默认「按报告」，可切换**：

| 模式 | 适用 | 说明 |
|---|---|---|
| **按报告**（默认） | 顺序核对 | 左侧文件列表 + 当前文件原文/字段并排，逐个推进 |
| **按指标** | 同一指标多份报告 | 按指标聚合，一次看到某指标的所有来源值 |
| **仅看待处理** | 收尾阶段 | 隐藏已确认，只显示待核对项 |

### 4.3 界面结构（按报告模式）

```text
┌─ 报告核对 ─────────────────────────────────────────────┐
│ [按报告] [按指标] [仅看待处理]      已确认 7/12 · 待核对 5 │
├──────────────┬─────────────────────┬───────────────────┤
│ 文件（12）    │ 原文                 │ 候选字段（3 待确认）│
│              │                     │                   │
│ ✓ 化验单10-08 │ 生化检验报告单        │ 采样日期 2026-10-08│
│   12 项 已确认│                     │ 指标名  总胆红素    │
│ ▶ 化验单09-05 │ 总胆红素  3.2  ...   │ 数值    3.2       │
│   3 项 待核对 │ 白蛋白    31   ...   │ 单位    mg/dL     │
│ ○ CT报告09-28 │ CA19-9   148.0 ...   │ 参考范围 0.3–1.2   │
│   未开始      │                     │ 原件页码 第 1 页   │
│ ○ 病理07-20   │                     │ [确认] [跳过] [排除]│
│   未开始      │                     │                   │
│ …            │                     │                   │
├──────────────┴─────────────────────┴───────────────────┤
│ [确认并下一项]  [稍后核对]              ← 主操作固定底部 │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：

| 元素 | 规则 |
|---|---|
| 左侧文件列表 | 每份显示**核对进度**（如 `3 项待核对`、`✓ 已确认`），一眼看出还剩多少 |
| 进度条 | 顶部显示总体 `已确认 7/12`，跨文件累计 |
| 主操作 | **「确认并下一项」**，自动跳到下一份未完成文件，不需要用户找 |
| 字段级状态 | 待确认 / 已确认 / 已排除 / 缺失，各自可见 |

### 4.4 主流程：确认完一份自动推进

```text
核对第 1 份 → 点「确认并下一项」
  → 该文件标记完成
  → 自动跳到下一份「待核对」文件
  → 全部完成后显示汇总
```

不需要用户回列表再点下一份。这是多文件核对体验的关键。

### 4.5 按指标模式（解决跨文件比较）

同一指标可能出现在多份报告（如 CA19-9 在 5 张化验单里）：

```text
┌─ 按指标核对 ────────────────────────────────────────┐
│ 总胆红素                                             │
│ ┌─────────────────────────────────────────────────┐ │
│ │ 日期        数值    单位     来源         状态    │ │
│ │ 2026-10-08  3.2    mg/dL   化验单10-08  待确认   │ │
│ │ 2026-09-05  1.8    mg/dL   化验单09-05  ✓已确认  │ │
│ │ 2026-08-01  1.2    mg/dL   化验单08-01  ✓已确认  │ │
│ └─────────────────────────────────────────────────┘ │
│ 参考范围：0.3–1.2（各来源一致）                        │
│ [批量确认全部]  [逐条核对]                            │
└──────────────────────────────────────────────────────┘
```

**这个模式的价值**：一次看到同一指标的全部历史与来源，容易发现异常跳变与单位不一致。

### 4.6 冲突与重复的处理

| 情况 | 处理 |
|---|---|
| **同日期同指标不同值** | 标为冲突，两条都显示，要求用户选择保留哪条（不静默取一个） |
| **同文件重复导入** | 按 SHA256 去重，提示「此文件已收录」，不重复解析 |
| **单位不一致** | 两条分开显示，不自动换算；标注「单位不同，未合并」 |
| **参考范围不一致** | 各自显示，不合并 |
| **同指标名不同写法** | 归一表映射（如 `CA199` / `CA19-9`），保留原名 |

**冲突必须可见**。两份报告给出同一天不同的 CA19-9，用户必须知道——这可能是录入错误，也可能是不同检测方法。

### 4.7 批量操作的作用范围

| 操作 | 范围 |
|---|---|
| 批量确认 | **仅作用于当前筛选项**，且必须显示将影响多少条 |
| 全部跳过 | 允许，但需二次确认 |
| 全部排除 | 允许，但需二次确认（排除意味着这些候选不再出现） |

**不允许「一键确认全部」**。理由：这会让核对环节形同虚设，而核对的全部意义就是人工把关。最多允许「批量确认已选中的项」。

### 4.8 中断与恢复

| 场景 | 行为 |
|---|---|
| 用户中途关闭 | 已确认的保留；未确认的保持待核对状态 |
| 再次进入 | 恢复到上次停下的文件与字段 |
| 解析未完成 | 显示排队/进行中，不阻塞已解析文件的核对 |
| 部分文件解析失败 | 该文件标失败并说明原因，其余照常核对 |

### 4.9 无 AI 也能核对

**核对不依赖模型**。MinerU 给出文本，规则给出候选字段，用户手工核对与修正。没有模型配置时，链路退化为「解析文本 + 手工录入」，仍然可用。

## 5. 阶段⑤：入库

| 规则 | 说明 |
|---|---|
| 只有确认值入库 | 沿用 v0.3 主链 |
| 保留修订痕迹 | 人工修订值 + 原始抽取值 + 来源 + 确认时间 |
| 幂等 | 重复点击确认不产生重复记录（`candidateId` + revision） |
| 事务 | 候选状态与正式记录同事务提交 |

## 6. 失败与降级矩阵

| 失败点 | 用户看到 | 降级路径 |
|---|---|---|
| 本地提取无文本 | 「此文件为扫描件，需要 OCR」 | 询问是否用 MinerU |
| MinerU 超限 | 「文件超过 10 MB / 20 页」 | 本地分页后重试，或手工录入 |
| MinerU 限流 | 「解析服务繁忙」 | 排队重试；保留原件 |
| MinerU 失败 | 阶段 + 原因 + 重试 | 手工录入 |
| 网络不可用 | 「云端解析需要联网」 | 本地提取 + 手工录入 |
| 表格重建异常 | 标注「表格可能不完整」 | 显示原始 Markdown 供对照 |
| AI 抽取失败 | 阶段 + 原因 | 规则候选 + 手工录入 |
| 用户拒绝上云 | 不调用 MinerU | 数字版可用；扫描件手工录入 |

**任何一环失败都不能让用户卡住**。最低保障是：原件在、能手工录入、能导出。
