# 小胰宝工作台 · 临床搜索与匹配初筛规格

日期：2026-10-13 · 状态：**设计建议稿，供用户讨论；非已实现能力**。

上级文档：[SPEC-v0.4.md](./SPEC-v0.4.md) §3.2。本文定义**临床匹配**：患者入组档案、数据渠道配置、入排规则库、匹配度三档算法。

---

## 1. 定位与边界

### 1.1 这个模块做什么

把「病人情况」和「试验入排标准」放在同一张表上逐条比对，告诉用户**哪些条件已经满足、哪些可能冲突、哪些无法判断**，并且每一条都能说出来依据。

### 1.2 这个模块明确不做什么

| 不做 | 原因 |
|---|---|
| 输出「符合入组条件」 | 入组判断属于医生与研究中心，工作台没有这个资格 |
| 输出匹配度百分比或 0–100 分 | 分数会被当成入组概率，且掩盖「无法判定」的部分 |
| 自动报名、自动联系中心 | 越权且不可逆 |
| 推荐「最适合的试验」 | 这是治疗建议 |
| 把「无已知冲突」说成「适合」 | 措辞越界 |

### 1.3 核心设计立场

**匹配分析的价值在于「把该问的问题整理清楚」，不在于给出答案。**

一个家属拿着匹配分析去问医生：「这几个试验里，我们记录的治疗史和基因结果看起来不冲突，但免疫治疗的禁忌我们不确定，需要再确认什么？」——这是这个模块成功的样子。

## 2. 患者入组档案

匹配分析的输入。全部来自病情整理，**不重复录入**。

### 2.1 档案构成

| 分组 | 字段 | 来源 |
|---|---|---|
| **基本** | 年龄、性别、病种、确诊日期 | `Patient` |
| **基因/分子** | 基因突变记录、IHC 标志物（B7-H3、CLDN18.2、PD-L1、HER2、MSI/dMMR 等）、检测方法与标本、报告日期 | `GenomicAlteration` |
| **病理** | 组织学类型、分化程度、分期 | `ClinicalFact` |
| **并发症** | 主要并发症及状态（活动/既往/无/未知） | `ComorbidityStatus` |
| **治疗史** | 治疗线数、每线方案与药物、起止、疗效评价、终止原因 | `TreatmentLine` |
| **体能** | ECOG | `ClinicalFact` |
| **器官功能** | 血常规、肝肾功能、凝血等关键指标 | `Observation` |

### 2.2 档案完整度

匹配分析前显示档案完整度，列出**本次分析会用到但缺失的字段**。缺失不阻断分析，但对应规则会判为「无法判定」。

```text
入组档案完整度 9/12
缺失：ECOG 评分 · 乙肝/丙肝状态 · 凝血功能
→ 这些缺失会让部分条件显示「无法判定」
[补充字段]  [仍然开始分析]
```

### 2.3 治疗线数与病情整理的同步

见 SPEC-v0.4 §4.2。要点：

- `TreatmentLine` 是唯一权威来源，两个模块是同一数据的两个视图。
- 药物必须做**通用名归一**才能支持「用过 X 就不能入 Y」这类规则。

### 2.4 药物归一

| 项 | 规则 |
|---|---|
| 记录内容 | 原始名称（如「白蛋白紫杉醇」「nab-paclitaxel」「Abraxane」）+ 标准化通用名 |
| 归一表 | 可维护的药物别名 → 通用名映射；支持用户新增 |
| 未归一处理 | 标「名称待确认」，**不参与**既往用药规则的匹配（避免误判为「未用过」） |
| 归一依据 | 保留原始文本与归一记录，可追溯、可纠正 |

**关键风险**：如果把未归一的药默认当作「没用过」，会把「可能冲突」误判成「已满足」，这是最危险的错误方向。因此未归一必须导致「无法判定」，不能导致「已满足」。

## 3. 入排规则库

### 3.1 为什么需要规则库

试验的入排标准在源数据里是自由文本。要做逐条比对，必须先把文本变成可判断的条件。三种做法：

| 做法 | 评价 |
|---|---|
| 每次把原文交给模型判断 | 快，但不可复现、不可审计、每次结果可能不同。**医疗场景不可接受** |
| 纯人工逐条录入 | 可审计，但成本高到无法规模化 |
| **AI 抽取候选 + 人工确认生效** | **本稿采用**。成本可控，结果确定、可追溯 |

### 3.2 规则结构

一条规则 = 一段来源原文 + 一个结构化条件 + 一个确认状态。

```yaml
ruleId: rule-8f3a12
trialKey: NCT-xxxx-example
sourceText: "既往接受过伊立替康治疗的患者需排除"
sourceRef: { section: "排除标准", index: 7, hash: "..." }
ruleType: prior_medication_exclusion
condition:
  field: treatment.history.medications.normalizedName
  operator: contains
  value: "伊立替康"
  negation: true          # 排除类规则
confirmation:
  status: confirmed        # pending | confirmed | rejected
  confirmedBy: user
  confirmedAt: "2026-10-13T10:20:00+08:00"
ruleVersion: 1
```

### 3.3 规则类型清单

| 类型 | 判定字段 | 示例 |
|---|---|---|
| `age_range` | 年龄 | ≥18 岁 |
| `disease_type` | 病种 | 胰腺导管腺癌 |
| `histology` | 组织学 | 需组织学确诊 |
| `stage` | 分期 | 局部晚期或转移性 |
| `genomic_marker` | 基因/IHC | B7-H3 阳性表达 |
| `msi_status` | MSI/dMMR | MSI-H 或 dMMR |
| `prior_medication_exclusion` | 既往用药 | 未用过伊立替康 |
| `prior_medication_required` | 既往用药 | 既往接受过含吉西他滨方案 |
| `treatment_line` | 治疗线数 | 一线治疗失败后 |
| `comorbidity_exclusion` | 并发症 | 排除活动性消化道出血 |
| `organ_function` | 器官功能 | 总胆红素 ≤ 1.5×ULN |
| `ecog_range` | 体能 | ECOG 0–1 |
| `prior_therapy_count` | 治疗线数上限 | 既往治疗不超过 2 线 |
| `infection_status` | 感染 | 乙肝/HCV/HIV 状态 |
| `pregnancy` | 妊娠 | 排除妊娠期 |
| `other` | 无法结构化 | 保留原文，判为「无法判定」 |

`other` 是诚实做法：结构化不了的，明确标出来让人去核实，不硬套一个可能错的判断。

### 3.4 规则生命周期

```text
试验详情 → 「分析入排条件」
  → AI/规则引擎抽取候选规则（标 picked-from-text）
  → 用户逐条确认 / 修改 / 排除
  → 确认后的规则进入规则库，绑定规则版本
  → 匹配分析使用已确认规则
```

- 未确认规则**不参与**三档统计，单独列为「待确认规则」。
- 规则与试验绑定，试验数据更新后若原文变化，规则标「来源已变化，需复核」。
- 规则可跨试验复用（同一类药物排除条件），但复用需用户确认。

### 3.5 规则库初始来源

待用户确认（见 §8）。候选：

1. 用户自己常关注的试验，先建一批。
2. 社区维护的胰腺癌试验常见入排条件模板。
3. 从本地语料的入排标准文本批量抽取候选，人工过一遍。

## 4. 匹配度三档算法

### 4.1 判定单元

对每条**已确认**规则，用患者档案求值，得到三档之一：

| 档位 | 判定条件 | 含义 |
|---|---|---|
| **已满足** ✅ | 档案字段存在，且值满足条件 | 该条条件已满足 |
| **可能冲突** ⚠️ | 档案字段存在，且值**不**满足条件 | 该条条件可能不满足，需核实 |
| **无法判定** ❓ | 档案字段缺失、值为 `unknown`、药物未归一、规则为 `other` 类型 | 现有资料不足以判断 |

### 4.2 判定规则

```text
对每条已确认规则 r:
  v = 取档案字段 r.field 的值

  if v 不存在 或 v == unknown:        → 无法判定
  if r.field 是药物且未归一:            → 无法判定
  if r.ruleType == other:              → 无法判定
  if 条件求值为真:                      → 已满足
  else:                                → 可能冲突
```

**关键约束**：

- 缺失**永远**流向「无法判定」，绝不流向「已满足」。这是整个算法最重要的一条。
- 求值必须是确定性的：同样的档案 + 同样的规则版本 = 同样的结果。不调用模型做判定。
- 数值比较使用规则中声明的单位与参考基准（ULN 等），单位不一致时判「无法判定」而非换算猜测。

### 4.3 试验级汇总

单个试验的展示：

```text
试验标题                                      [收藏]
──────────────────────────────────────────────
已满足 8 项   可能冲突 2 项   无法判定 3 项   待确认规则 1 项
──────────────────────────────────────────────
⚠️ 可能冲突
   · 既往未接受伊立替康治疗
     你的记录：二线方案含「伊立替康」（2026-05-12 至 2026-07-30）
     来源：治疗记录 · 原文第 3 页
❓ 无法判定
   · ECOG 体能评分 0–1
     缺失：未记录 ECOG
     [补充 ECOG]
✅ 已满足
   · 年龄 ≥18 岁 — 62 岁
   · 组织学确诊胰腺癌 — 有病理记录
   ...
```

### 4.4 汇总层面的表达约束

| 禁止 | 使用 |
|---|---|
| 「匹配度 75%」 | 三个数字分别列出 |
| 「高匹配」「推荐」 | 「无已知冲突」 |
| 「不符合条件」 | 「有 2 项可能冲突」 |
| 把无法判定合并进已满足 | 始终独立列出 |
| 用绿/红给试验排名 | 中性列表，按用户选择排序 |

**排序规则**：默认按用户关注的记录时间或数据来源顺序；提供手动排序。不提供「按匹配度排序」，因为它会暗示推荐。

### 4.5 可复现性

每次匹配分析生成 `MatchAssessment`：

- 记录档案 revision（生成时的档案快照版本）
- 记录规则集版本
- 记录逐条判定结果
- 档案或规则变更后，旧评估标「档案已更新，建议重新评估」，保留旧结果供对比

## 5. 数据渠道配置管理

### 5.1 两类渠道

用户提到的「universal search skills + 数据库」，对应两类：

| 类型 | 说明 | 示例 |
|---|---|---|
| **skill 渠道** | 通过技能/工具调用的检索能力 | 统一检索服务、在线检索技能 |
| **数据库渠道** | 本地或远端的结构化数据源 | ChiCTR 归档、CDE 归档、CTV 索引 |

现有集成设计已核实六个 adapters（见 INTEGRATION-DESIGN.md §2.1），但**六个可注册来源不等于六个默认可用来源**。

### 5.2 渠道配置界面

```text
渠道配置
─────────────────────────────────────────────
本地数据
  ● ChiCTR 胰腺癌归档      就绪 · 468 条 · 截至 2026-10-05
  ● CDE 社区归档           就绪 · 139 条 · 抓取 2026-08-14 至 09-29
  ○ CTV 索引               未就绪 · 需要运行组件
在线来源（可选）
  ○ ChiCTR 在线            未启用
  ○ ICTRP                  未启用 · 需要额外运行环境
```

每个渠道显示：**状态 · 记录数 · 数据覆盖时间 · 最后检查时间 · 失败原因**。

### 5.3 渠道状态语义

| 状态 | 含义 | 对匹配的影响 |
|---|---|---|
| `ready` | 可用 | 正常参与检索 |
| `partial` | 部分可用 | 参与，但结果标「覆盖不完整」 |
| `needs-setup` | 缺少运行组件或数据 | 不参与，明确说明缺什么 |
| `failed` | 读取失败 | 不参与，提供重试 |
| `disabled` | 用户关闭 | 不参与 |
| `updating` | 更新中 | 用旧版本参与 |

**关键约束**：未就绪渠道**不能**显示成「没有试验」。必须区分「这个渠道里没有」和「这个渠道没在查」。

### 5.4 检索范围提示

每次检索结果显示：

```text
本次检索覆盖 2/4 个渠道
未参与：CTV 索引（未就绪）· ICTRP（未启用）
数据截至：2026-10-05（ChiCTR）· 2026-09-29（CDE）
```

## 6. 与检索的关系

```text
试验检索（关键词/筛选）        ← 找候选试验
        ↓ 用户选择某个试验
入排条件抽取 → 人工确认规则    ← 把文本变成规则
        ↓
匹配分析（逐条判定）           ← 与档案比对
        ↓
三档结果 + 依据
```

检索和匹配是两步，不合并。理由：

- 检索是「有哪些试验」的问题；匹配是「这个试验和我什么关系」的问题。
- 合并会诱导用户用匹配结果代替检索，从而只看到已有规则的试验。
- 检索结果里**可以**显示「已分析」标记，但不能用匹配结果过滤掉未分析的试验。

## 7. 失败与边界

| 场景 | 表现 |
|---|---|
| 档案缺关键字段 | 相关规则判「无法判定」；顶部提示缺什么 |
| 药物未归一 | 既往用药规则判「无法判定」；提供归一入口 |
| 规则未确认 | 单列「待确认规则」，不计入三档 |
| 规则类型为 `other` | 原样显示原文，判「无法判定」，提示需医生核实 |
| 试验源文本更新 | 规则标「来源已变化，需复核」，不静默沿用 |
| 渠道全部未就绪 | 明确说明「当前没有可用渠道」，不显示 0 条结果 |
| 单位不一致 | 判「无法判定」，不做换算猜测 |
| 档案在分析后变更 | 旧评估标「需重新评估」，保留供对比 |

## 9. v3 临床匹配患者视图

入组档案采用方便扫读的无强调边框表格。分子检测表列出靶点、突变类型、丰度、来源、记录证据；IHC 表列出项目、结果、强度/比例、来源、记录证据。

- 首屏展示 KRAS、TP53、ARID1A、STK11、CLDN18.2、TROP2、B7-H3、C-MET、HER2 等当前报告已确认项目。
- 其他已测和未检测项目放入可展开区域，不删除。未检测表示报告未覆盖或尚未录入，不等于阴性。
- “记录证据”只说明是否可追溯到患者原始报告，例如「A · 原件已确认」；它不是临床获益等级、疗效等级或入组资格。
- CLDN18.2、TROP2 等 IHC 强度和阳性比例严格按报告保存；不得把“阳性 20%、弱—中等强度”改写为“3+”。

五个子页各自承担一种任务：入组档案展示患者资料；试验检索展示候选线索；匹配分析展示可对照条件、待补资料与研究中心确认项；收藏展示保存的线索、备注和快照；数据来源展示本机数据版本、覆盖范围与同步状态。各页不重复完整检索结果。
