## 2. MinerU（文档解析）

### 2.1 为什么需要它

用户的真实病历有三类：

| 类型 | 占比（样本观察） | 现有链路能否处理 |
|---|---|---|
| 数字版 PDF（可选中文字） | 部分 | ✅ 本地文本提取即可 |
| **扫描件 PDF / 手机拍照** | **多数** | ❌ 必须 OCR |
| Word / Excel 导出的报告 | 少量 | ⚠️ 需转换 |

**「智能病历整理」的核心难点是 OCR，不是 AI 抽取**。医院报告大量是扫描件或拍照，没有文本层。因此需要一个 PDF→结构化文本的解析器。

### 2.2 实测结论（本轮）

已在本机实测 `mineru-open-api` v0.5.9。

| 检查 | 结果 |
|---|---|
| CLI 是否安装 | ✅ 已安装（`~/.nvm/.../mineru-open-api`，v0.5.9） |
| Token 是否已配置 | ✅ `~/.mineru/config.yaml` 存在 |
| `flash-extract`（免 token） | ✅ 成功，1 页医疗 PDF → 2.6 KB Markdown |
| `extract --model pipeline`（需 token） | ✅ 成功，含图片提取 |
| 中文识别 | ✅ 良好（胰腺癌、免疫组化、方案名均正确） |
| **表格保留结构** | ⚠️ 输出为 HTML `<table>`，14 行可解析，**但含 rowspan/colspan 合并，需自行重建网格** |
| 图片提取 | ✅ precision 模式会导出内嵌图片到 `images/` |

**两模式输出质量对比**（同一份病历）：

| 项 | flash-extract | extract --model pipeline |
|---|---|---|
| `STK11p.L50*` | 粘连 | ✅ `STK11 p.L50*` 正确分词 |
| `TMB3.0` | 粘连 | ✅ `TMB 3.0` |
| `PETCT` | 粘连 | ✅ `PET CT` |
| `AG 方案8周期` | 粘连 | ✅ `AG 方案 8周期` |
| 内嵌图片 | 不导出 | ✅ 导出到 `images/` |

**结论：precision 模式（pipeline）质量明显更好，建议作为默认。flash 作为无 token 时的降级路径。**

### 2.3 两模式限制（来自官方 SKILL.md，非实测）

| | flash-extract | extract |
|---|---|---|
| 需要 token | ❌ 不需要 | ✅ 需要 |
| **文件大小上限** | **10 MB** | 更高 |
| **页数上限** | **20 页** | 更高 |
| 批量 | ❌ | ✅ |
| 输出格式 | 仅 Markdown | md/html/latex/docx/json |
| 模型 | pipeline | vlm / pipeline / MinerU-HTML |
| 限流 | 可能 HTTP 429 | 较宽松 |

**这三条限制对本项目影响很大**：

1. **10 MB 上限**：一份增强 CT 报告或含多图的出院小结很容易超过。实测样本中李菊病历 2.2 MB 尚可，但扫描件常见 10–50 MB。
2. **20 页上限**：完整住院病历常超 20 页。
3. **flash 无批量**：用户一次导入多份报告时会逐个调用。

**应对**：默认走 precision 模式；对超限文件先做**本地预压缩或分页**（见 §2.5）。

### 2.4 模型选择：pipeline vs vlm

| | vlm | pipeline |
|---|---|---|
| 准确率 | 更高（复杂版式） | 标准 |
| **幻觉风险** | **可能产生幻觉文本** | **无幻觉** |

**医疗场景必须选 `pipeline`。**

理由：vlm 可能生成原文中不存在的文字。在病历场景，这意味着可能凭空产生一个检验值或一个药名，而用户未必能发现。pipeline 输出可保证「有的就是有的，没有的不编」。

代价是复杂版式的准确率略低——但**宁可漏，不可编**。抽取结果本来就要人工核对，漏了能被发现，编了则难以察觉。

### 2.5 集成设计

**调用方式**：作为工作台服务端子进程调用，不在 renderer 直接调用。

```text
用户导入文件
  → 判定类型（数字版 / 扫描件 / 其他格式）
  → 数字版：本地文本提取（快，离线）
  → 扫描件 / 图片 / Word：调用 MinerU
      → 大小或页数超限：先本地分页或降采样
      → 默认 --model pipeline（无幻觉）
      → 输出 Markdown + images/
  → 表格 HTML 重建为网格结构
  → 进入候选字段抽取
```

**关键设计**：

| 设计 | 理由 |
|---|---|
| **默认 pipeline，不默认 vlm** | 无幻觉优先（§2.4） |
| **超限先本地分页** | 10 MB / 20 页限制会拦住真实病历 |
| **表格必须重建网格** | 原始 HTML 带 rowspan/colspan，直接展示不可读 |
| **解析结果落盘** | 解析一次可复用，避免重复上传与重复计费 |
| **失败保留原件** | 解析失败不影响原件与手工录入 |

### 2.6 隐私问题（必须处理）

MinerU 是**云端服务**：文档内容会传输到 `mineru.net` 做服务端解析。

对病历数据而言这是重大决策。必须做到：

| 要求 | 说明 |
|---|---|
| **明确告知** | 首次使用前提示「将把所选文件上传到 MinerU 云端解析」，列出文件数与去向 |
| **可关闭** | 用户可禁用云端解析，仅用本地文本提取（扫描件则需手工录入） |
| **不默认开启** | 作为可选能力，不假设用户同意上传病历 |
| **不与其他数据混合** | MinerU 只收到文件本身，不附带患者档案、基因结果等 |
| **记录解析来源** | 每条抽取结果标注「由 MinerU 解析」或「本地提取」，便于追溯 |

**这是与「病历留在本机」原则的直接冲突点**，必须在设计文档与界面里都写清楚，不能含糊。

**替代方案**（若用户不接受上云）：

| 方案 | 代价 |
|---|---|
| 本地 OCR（如 Tesseract / PaddleOCR） | 中文医学表格准确率明显低于 MinerU |
| 完全手工录入 | 用户负担重 |
| 仅支持数字版 PDF | 覆盖不了扫描件 |

本文档不替用户做决定，只列出选项。**倾向**：把 MinerU 作为默认推荐但可关闭，同时在依赖里预留本地 OCR 的位置。

### 2.7 Token 申请与配置（已实测路径）

**申请流程**（已访问 mineru.net 确认页面存在）：

1. 访问 mineru.net 注册 / 登录
2. 进入「API」→「API 管理」页面
3. 创建 Token 并复制
4. 在工作台**设置 → 文档解析**粘贴，点「校验并保存」

**Token 形态**：以 `sk-` 开头，本机实测样本长度约 20 字符。

**存放位置**：实测 CLI 存在 `~/.mineru/config.yaml`，字段为 `token`。

**决策（已确认）：复用 `~/.mineru/config.yaml`，不另建存储。**

已实测：文件为单行 `token: <值>`，权限 0600；解析优先级为 `--token` > `MINERU_TOKEN` > 配置文件。

| 好处 | 代价与对策 |
|---|---|
| 设置页填了命令行也能用，无两份 token | 需原子写入并保留其它键 |
| 命令行配了工作台开箱即用 | 需处理 `~/.mineru/` 不存在的情况 |
| 兼容官方文档路径 | 环境变量存在时需提示用户（否则「填了没用」） |

完整写入规则、边界情况见 [SETTINGS-SPEC §3.5](./SETTINGS-SPEC.md)。

**密钥处理规则**见 [SETTINGS-SPEC §4](./SETTINGS-SPEC.md)：不回显、不进日志、不进导出、不写业务资料根。

### 2.8 集成门槛（实现前必须解决）

| # | 门槛 | 说明 |
|---|---|---|
| 1 | **打包与分发** | npm 包 `mineru-open-api` 需随工作台交付还是要求用户自装？若随包，体积与平台（含 Go 二进制路径）需验证 |

| 6 | **表格重建质量** | rowspan/colspan 重建后是否与原表一致，需样本验证 |

| 项 | 说明 |
|---|---|

| 依赖 | 宿主已配置的模型；无模型时手工录入仍可用 |
