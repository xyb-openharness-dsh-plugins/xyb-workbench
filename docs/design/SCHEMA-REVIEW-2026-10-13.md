# 小胰宝数据 Schema 审查记录

日期：2026-10-13
范围：`DATA-SCHEMA-DESIGN.md`、`SCHEMA-SPEC.md`、`DATA-FLOW-SPEC.md`、`SPEC-v0.4.md`、`DASHBOARD-SPEC.md`、`MATCHING-SPEC.md`、`TIMELINE-SPEC.md`、`CARE-MANAGEMENT-SPEC.md`、`REVIEW-SPEC.md`、`INTEGRATION-DESIGN.md`、`REPORT-GENERATION-DESIGN.md`，以及 `prototype-v2.html`、`prototype-v3.html`、`V2-V3-PARITY-AUDIT.md`。
性质：**设计审查**。本次未修改上述资料，也未发现小胰宝专属建表迁移与 schema 测试；因此下列结论针对设计完整性，不表示已实现的数据库已通过验收。

---

## 1. 总体结论

**现有 schema 不能视为已完整覆盖 v2/v3，也不适合直接照此建库。**

方向正确：分层抽取、确认事实单一来源、结论快照可复现、前端迭代不改历史数据，这些原则成立。主要问题不是原则错误，而是**尚未收敛成一套可直接实施的规范模型**：

1. 两份 schema 文档存在实体口径冲突。
2. 匹配与试验相关模型缺少稳定键与冻结输入的完整定义。
3. 若干 v2 已要求的领域实体未进入新设计。
4. 当前事实实时计算与结论保留快照的分界仍有歧义。
5. 迁移与版本兼容仍是原则描述，缺少可执行方案与测试。

**v2/v3 功能不一致本身不是阻碍建库的理由，恰恰是本次设计的核心约束。** 因为 v3 尚未与 v2 功能一致（`V2-V3-PARITY-AUDIT.md:6–21`），schema 必须同时容纳「v2 已有能力」与「v3 当前展示形态」，并允许前端在二者之间演进而不迁移患者数据。因此第 6 节单独给出进化弹性设计要求。

---

## 2. 阻塞项：领域模型未统一

| 冲突点 | 依据 | 影响 |
|---|---|---|
| `DATA-SCHEMA-DESIGN.md:8–10, 114–142` 将 `TreatmentLine` 拆为 `treatment_plan`/`treatment_event`，并把毒性、管路、症状等泛化为 `care_event` | 与 `SCHEMA-SPEC.md:134–159` 的治疗线 + `treatment_line_drug` 子表、`SCHEMA-SPEC.md:170–197` 的 `catheter_record` + `catheter_maintenance` 不一致 | 线数、药物明细、药物归一状态、CTCAE 分级、管路维护历史可能无法结构化落库或无法供匹配复用 |
| 名称映射不能替代结构定义 | `SPEC-v0.4.md:300–319` | 只写「对应某实体」无法回答子表、枚举、空值语义、索引与约束问题 |

**要求**：先产出一份规范化实体清单与关系图，再写 DDL。治疗线—药物明细、管路—维护记录必须保留为独立结构，不得用通用 JSON 事件替代。泛化事件表只能作为补充，不能成为毒性、并发症、管路等事实的唯一存储。

## 3. 阻塞项：匹配结论不足以复现

| 缺失 | 依据 | 影响 |
|---|---|---|
| `trial_match_snapshot` 未完整锁定稳定试验键、来源数据代次、规则原文及版本、当时参与判断的事实取值、判定器版本 | `DATA-SCHEMA-DESIGN.md:160–175`；`MATCHING-SPEC.md:227–234`；`INTEGRATION-DESIGN.md:215–274` | 数据集或规则更新后，用户当时看到的结果无法解释，也无法复算 |
| 公共试验数据与患者收藏/笔记的边界未落到表结构 | `SCHEMA-SPEC.md:251–261`；`INTEGRATION-DESIGN.md:226, 272` | 数据包替换后收藏断裂，或用户内容被公共更新覆盖 |
| 联系与跟进记录依附某次匹配快照 | `DATA-SCHEMA-DESIGN.md:173` | 重新评估后历史跟进记录难以延续 |

**要求**：

- 公共试验库与患者库物理分离；收藏与笔记用**稳定试验键**（来源 + 来源记录 ID）关联，不用自增主键。
- 每次评估冻结：输入的档案版本与取值、规则集版本与原文、来源与数据代次、判定器版本、逐条结果与缺失项。
- 跟进与联系记录独立于某一次评估，可跨多次评估延续。

## 4. 阻塞项：v2 已要求的实体未覆盖

v3 页面较简略不应导致领域能力被删除。以下实体或结构在新设计中缺失或不明确：

| 实体 / 结构 | 支撑功能 | 依据 |
|---|---|---|
| `TimelineAnnotation` | 一图秀竖线标注、偏移、导入与修正记录 | `TIMELINE-SPEC.md:109–133`；`SPEC-v0.4.md:308` |
| `TimelineDataset` | CSV 导入血缘、行数、修正记录、导出记录 | `SPEC-v0.4.md:309` |
| `TrialBookmark` / `TrialNote` | 收藏快照、备注、跟进状态、来源更新比较 | `V2-V3-PARITY-AUDIT.md:38–43`；`INTEGRATION-DESIGN.md:226` |
| `DataChannel` | 渠道就绪、失败、重试、覆盖范围与更新状态 | `MATCHING-SPEC.md:238–276` |
| 管路维护记录独立子结构 | 「距上次维护 N 天」、维护历史趋势 | `DATA-FLOW-SPEC.md:107–122`；`SCHEMA-SPEC.md:189–197` |
| 毒性记录的 CTCAE 分级与转归 | 全程管理毒性子页 | `CARE-MANAGEMENT-SPEC.md:3.1` |

**要求**：建立「功能 → 领域实体 → 写入命令 → 读模型 → 验收用例」追踪表，逐项证明 v2 已有能力和 v3 目标形态都能由模型支撑。

## 5. 高优先级：语义与迁移

### 5.1 事实实时计算与结论保留快照的边界

| 现状 | 依据 | 风险 |
|---|---|---|
| 当前读模型按事实实时生成 | `DATA-SCHEMA-DESIGN.md:43–45` | 与结论不自动重算并存时，未定义「哪些派生值必须实时、哪些结论必须冻结」 |
| 看板分级被列为不自动重算的结论，同时当前看板又按实时计算 | `DATA-FLOW-SPEC.md:48–72`；`DASHBOARD-SPEC.md:302–320` | 同一「分级」概念两种语义，实现时易产生静默重算或永不更新 |

**要求**：

- 当前事实与确定性派生值：读取时计算，不存当前状态副本。
- 匹配评估等结论：保存不可静默改写的评估结果；档案、规则或来源变化时给出「建议重新评估」提示，由用户发起新评估。
- 历史看板：仅在用户主动保存时冻结，不用于渲染当前状态。

### 5.2 临床值与证据约束

- `measurement` 未完整承接 `SCHEMA-SPEC.md:101–132` 的比较符、原文值、单位标准化与换算状态，「未检测」与「阴性」的区分也未统一。
- `gene_finding`、`ihc_result` 作为病理报告子项，未明确每条结果各自的页内证据与来源。
- 手工录入允许无文档来源，但必须记录来源类型与录入者，不能与未记录混淆。

### 5.3 迁移与版本兼容

现有描述停留在原则：`DATA-SCHEMA-DESIGN.md:216–228` 要求读模型版本化并保留两个发布周期；`SCHEMA-SPEC.md:265–270` 要求先备份、单向可重放迁移。桌面应用可能长期离线，「两个周期」不能保证旧客户端可读升级后的库。

**要求**：定义数据库版本号、迁移前置校验、备份与恢复流程；采用「扩展 → 双读/双写或转换 → 切换 → 延后收缩」；分别测试**新程序读旧库**与**旧程序遭遇新库**的行为。

## 6. 面向 v2/v3 不一致的进化弹性要求

v2/v3 功能不一致是持续状态，schema 必须显式支持「前端不断变、领域模型少变、历史数据不迁移」。

### 6.1 分层演进

| 层 | 变化频率 | 约束 |
|---|---|---|
| 领域事实 | 低 | 仅在真实新增临床事实时扩展，不因页面改版变动 |
| 扩展字段 | 中 | 新增字段不得改写旧字段语义；需要筛选、排序、画趋势的字段升为正式列并建索引 |
| 读模型契约 | 中高 | 版本化，容忍未知字段，旧契约延后下线 |
| 界面 | 高 | 仅消费读模型，变更不产生迁移 |

### 6.2 覆盖能力要求

- **双向覆盖**：既要支撑 v2 已有能力（跨页比对、入组档案、规则分组分析、营养计算链路、量表历史、管路维护等），也要允许 v3 以简化形态先行展示；简化展示不得删减领域字段。
- **能力开关与页面能力声明**：页面未实现的子功能应表现为明确状态（未开放、待补齐），不得用空数据冒充已支持。
- **同一事实多形态呈现**：v2 完整视图与 v3 简化视图读取同一份事实，不维护两份页面数据。
- **缺失即缺失**：新字段为空时显示未记录或隐藏卡片，不得解释为正常、阴性或无症状。

### 6.3 变更判定

沿用 `SCHEMA-SPEC.md:295–308`：改的是「数据是什么」才动 schema，改的是「数据怎么看」只动界面。v3 补齐 v2 功能时，若发现领域模型缺实体，应补模型；若只是展示形态不同，不应改表。

1. **产出规范化实体清单**：统一命名、关系、状态枚举、时间语义、证据字段，消除两份 schema 文档冲突。→ 已产出 [SCHEMA-CANONICAL-MODEL-DRAFT.md](./SCHEMA-CANONICAL-MODEL-DRAFT.md)
2. **补关键结构 DDL**：治疗线—药物明细、分子/病理结果、管路—维护、毒性、时间轴标注与导入血缘、试验稳定键与收藏笔记、渠道状态。→ 已产出 `schema/0001_initial.sql`（53 张表，已通过内存库执行、幂等重跑与约束冒烟测试）、`schema/migrate.mjs`（迁移执行器）、`schema/MIGRATION-RUNBOOK.md`（备份、兼容模式与测试清单）。
3. **定义冻结契约**：匹配评估与报告快照的输入、规则、来源版本、判定器版本与逐条结果。
4. **定义读模型与命令清单**：版本化命名、兼容规则、命令事务与审计字段。
5. **写可执行迁移与版本兼容测试**：覆盖新程序读旧库、旧程序遇新库、备份恢复一致性。→ 已产出执行器与操作手册；待补自动化测试脚本（旧库样本 + 中断重放 + 恢复校验）。
6. **建立功能追溯矩阵**：逐条映射 v2 功能、v3 形态、所需实体与验收用例。→ 已产出 [SCHEMA-FUNCTION-TRACEABILITY-DRAFT.md](./SCHEMA-FUNCTION-TRACEABILITY-DRAFT.md)
7. **明确未决项**：基因与病理是否共用表、指标与分子结果是否合并、公共试验数据是独立库还是同库分表、快照持久化范围、字段级加密列清单。

## 8. 验收口径

- 不得因 v3 尚未实现某功能而宣称 schema 不支持该功能。
- 不得将「设计已覆盖」表述为「实现已通过验收」。
- 调整 v3 卡片布局不应迁移患者数据；新增一个字段不应破坏旧报告与旧匹配评估。
