## 1. 为什么需要统一设置页

### 1.1 现状问题

配置散落在各模块：

| 配置项 | 当前位置 | 问题 |
|---|---|---|
| 检索渠道启用/状态 | 临床匹配 → 渠道配置 | 用户找「设置」时会先去顶栏 |
| MinerU token | 无 | 未设计 |
| 业务资料根目录 | 资料库 → 资料位置 | 埋在二级页 |
| 备份与恢复 | 无正式入口 | 未设计 |

用户已经形成了「设置应该有个统一地方」的预期。分散的配置让每个新能力都要重新决定放哪。

### 1.2 为什么不新增一级 Tab

一级 Tab 已经是 7 个（看板/病情整理/病情一图秀/临床匹配/营养管理/心理支持/全程管理）。

**设置不是一级任务，是低频配置。** 把它提为一级 Tab 有两个代价：

1. 挤占导航宽度（实测 1280px 已接近临界，见 UI-DESIGN）
2. 每天看病情的人和每月改配置的人共用同一排导航，权重错配

**结论：用顶栏齿轮入口，不占一级 Tab。**

## 2. 入口与位置

```text
┌─ 小胰宝        患者 ▾          资料留在本机   ⚙ 设置   ✧ AI 协助 ─┐
```

- 齿轮位于「AI 协助」左侧，顶栏右端
- 图标 + 文字（不只图标，避免猜测）
- 点击后打开设置弹窗，按 v3 分区完整呈现数据来源、文档解析、存储备份和工作台范围

**交互按用户最新要求**：采用 v3 模态弹窗；内容区独立滚动，关闭时回到原 Tab。此前“整页替换”的建议已被此决策覆盖。

**面包屑**：设置页左上角显示「← 返回 <原页面>」，返回时恢复原 Tab 与滚动位置。

## 3. 三组配置

```text
设置
├─ 01  数据来源        检索渠道的启用与状态
├─ 02  文档解析        本地提取 / MinerU 云端解析 + token
└─ 03  存储与备份      业务资料根、备份与恢复
```

### 3.1 数据来源

把原「临床匹配 → 渠道配置」迁移过来，内容不变（见 [MATCHING-SPEC §5](./MATCHING-SPEC.md)）：

- 本地数据：ChiCTR 归档 / CDE 归档 / CTV 索引
- 在线来源：ChiCTR 在线 / ICTRP
- 每项显示：状态、记录数、覆盖时间、最后检查时间、失败原因

**迁移后的处理**：临床匹配的「渠道配置」二级 Tab 保留，但改为**跳转到设置页**（不维护两份界面）。同时在设置页说明「此配置影响临床匹配的检索范围」。

### 3.2 文档解析

#### 3.2.1 解析方式选择

```text
○ MinerU 解析（默认推荐）
    默认使用随包的公益 API Token 调用 pipeline；用户 Token 可覆盖。
    凭据认证失败时提醒用户申请替换，并尝试 Flash 免费解析（尚未实现，见下）。
    · Flash 不需 Token，但所选文件会发送到 MinerU 云服务；结果只有 markdown，
      不保证表格结构，界面必须标注「轻量模式，结果可能不准」
    · 用户替换 Token 保存在本机 .secrets/mineru.json（唯一本地密钥文件），
      不回传到 UI 或写进患者库；环境变量 MINERU_TOKEN 仅作临时覆盖
    · TXT / MD / CSV 始终优先本地解析

○ 仅本地解析
    仅支持 TXT / MD / CSV 的本机抽取；PDF、图片和 Office 原件可归档，但不做 OCR。
```

**默认解析器为 MinerU；首次解析会先弹出云端说明并要求明确确认。**未确认前不上传、不调用 MinerU。Flash 与 API 都是云端处理；此处说明优先级取代本文件此前“仅本地作为默认”的旧决策。

> **实施状态（2026-10-22 核查）**：Flash 通道（`POST /api/v1/agent/parse/file`）在小 X 宝家族**尚未实现**，全家族 0 处调用。本文件保留 Flash 条款作为规划口径，代码里目前只有 API v4 四步一条通路。在 Flash 落地前，认证失败时只能提示用户替换 Token 或改「仅本地解析」，不得假装已降级到 Flash。

#### 3.2.2 隐私告知（切到云端时必须展示）

首次使用 MinerU 时，设置弹窗内展示说明并要求用户勾选确认：

```text
启用后，你导入的扫描件与图片会上传到 MinerU 云端解析。
· 传输内容：仅你所选的文件本身
· 不会传输：患者档案、基因结果、治疗记录、收藏与笔记
· 处理方式：服务端解析完成后不保留
· 可随时关闭

[了解 MinerU 隐私政策]   [我了解，启用]
```

**必须点「我了解，启用」才生效**，不默认勾选。

#### 3.2.3 Token 替换与过期降级

```text
MinerU API Token（可选替换公益 Token） [ 输入新 Token ]
┌──────────────────────────────────────────────┐
│ sk-······································    │  ← 密码型，带显示/隐藏
└──────────────────────────────────────────────┘
[ 校验并保存 ]   [ 如何申请？ ]

状态：内置公益 Token · API 解析可用
```

**交互规则**：

| 规则 | 说明 |
|---|---|
| 密码型输入 | 默认隐藏，提供「显示」切换 |
| **只能校验，不能回显** | 保存后只显示后 4 位（`sk-····pJqM`），不提供「查看完整值」 |
| 保存前先校验 | 点「校验并保存」调用一次轻量接口；成功才写入 |
| 校验失败给原因 | 401 = token 无效；429 = 配额用尽；网络错误单独提示 |
| 用户 Token 覆盖 | 本机 `.secrets/mineru.json`（唯一持久来源）> `MINERU_TOKEN` 环境变量（仅作临时覆盖）> 随包公益 Token |
| 过期回退 | 认证失败时提醒用户申请新 Token，并自动尝试 Flash；成功时明确显示为 Flash 降级解析（Flash 通道未实现，见 §3.2.1 实施状态） |
| **过期提醒（2026-10-22 新增，已实现）** | 解析失败且错误由 Token 引起时，界面顶部留一条独立提醒（不随一般提示消失）：一句话说清「只影响扫描件/照片自动识别、原件在本机、已确认指标不受影响」，并给三个动作——① 打开 `https://mineru.net/apiManage/token` 申请/重置 ② 在设置里填入新 Token ③ **让 Agent 用一段话提醒患者怎么换**（把提示词放进右侧原生会话，由患者自己按发送）。判定方式不新增状态码：后端错误消息里含该申请地址即视为 Token 问题，前后端只认这一个约定 |
| Flash 限制 | 单个文件最多 10 MB / 20 页；超限或失败保留原件并提示申请新 Token 或稍后重试 |
| **不显示在日志/导出** | 见 §4 |

**「如何申请？」展开后**：

```text
1. 访问 mineru.net 并注册/登录
2. 进入「API」→「API 管理」页面
3. 创建 Token 并复制
4. 回到这里粘贴，点「校验并保存」

[ 打开 mineru.net/token 申请页 ]   ← 外部链接，点击前提示去向
```

**为什么应用内填入而不是引导用 CLI**：用户已经装好了工作台，再要求开终端跑 `mineru-open-api auth` 会挡住大部分人。工作台首次开箱用公益凭据；用户也可应用内替换自己的 Token。随包凭据会随公开安装包分发，使用前应确认公益配额策略和维护安排。

#### 3.2.4 解析模型

```text
解析模型
● pipeline（默认）    面向病历优先保留来源内容，不做生成式补写
```

默认 pipeline，理由见 [RESOURCE-DEPENDENCIES §2.4](./RESOURCE-DEPENDENCIES.md)。VLM 可能生成原文中不存在的内容，因此当前病历流程不向用户提供 VLM 选项。

**口径来源**：2026-10-22 跨工作台统一口径决定「默认模型 = pipeline」，本仓代码里 `MINERU_MODEL_DEFAULT = 'pipeline'`、接口拒该参数时回退 `vlm`。设置里 `settings.mineruModel` 可以传 `'vlm'` 覆盖，但**目前没有界面入口**，属预留口子，不要当成已交付能力。

### 3.3 存储与备份

| 项 | 内容 |
|---|---|
| 业务资料根 | 显示当前路径 + 「更改位置」（走宿主目录选择器） |
| 已用空间 | 原件 / 派生文件 / 数据库分别占用 |
| 备份 | 「立即备份」+ 上次备份时间 + 备份位置 |
| 恢复 | 「从备份恢复」— 需二次确认，说明会覆盖什么 |

**不在这里放**：模型配置（宿主管理）、主题（宿主管理）、深色模式（跟随宿主）。**避免冒充宿主设置**。

## 3.5 Token 存放：`.secrets/mineru.json` 唯一（**2026-10-22 改定**）

**决策：工作台只读写自己的 `.secrets/mineru.json`，不再读写 `~/.mineru/config.yaml`。**

本文件此前（2026-10-13 版本）的决策是「与官方 CLI 共用 `~/.mineru/config.yaml`」。该决策在 2026-10-22 被覆盖，原因是跨工作台统一口径要求**`.secrets/mineru.json` 为唯一本地密钥文件**，避免出现「同一个 Token 存两处、哪份才算数」的分叉。下面是现行口径。

### 3.5.1 文件格式与位置

路径：仓根下的 `.secrets/mineru.json`（与 `dsh/settings.js` 同仓，用 `import.meta.url` 解析，不依赖 `process.cwd()`）。

```json
{ "token": "sk-xxxxx" }
```

| 项 | 现行要求 |
|---|---|
| 文件路径 | `<workbench>/.secrets/mineru.json` |
| 格式 | 单键 JSON，键名 `token` |
| 文件权限 | `0600`（写入时显式 `chmod`，仅所有者可读写） |
| 目录创建 | `.secrets/` 不存在时按需创建 |
| 版本控制 | 已在 `.gitignore`，**不得提交** |

### 3.5.2 token 解析优先级（现行）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 显式传入的 `token` 参数 | 调用方直接给值，最高 |
| 2 | `.secrets/mineru.json` | **唯一持久来源**；`source` 标记为 `secret-file` |
| 3 | `MINERU_TOKEN` 环境变量 | **仅作临时覆盖**；`source` 标记为 `environment` |
| 4 | 随包公益 Token | 兜底；`source` 标记为 `bundled-community` |

**注意优先级顺序**：文件高于 env。这与旧版（env > config.yaml）相反。理由是「文件是用户在工作台里主动保存的、可复查的选择」，env 更像一次临时试验；若 env 长期覆盖文件，用户在设置页保存后不生效会无从排查。需要在本次会话里临时换 Token 时用 env，长期换就用设置页。

`source` 必须原样回给界面，不要在 UI 侧自己猜。

### 3.5.3 不再读写的旧路径

| 旧行为 | 现状 |
|---|---|
| 从 `~/.mineru/config.yaml` 读 token | **已删除**（`mineruConfigFile()` 函数一并移除） |
| 把 token 写成 `token: sk-xxx` YAML 行写回 `~/.mineru/` | **已删除** |
| 设置页文案提到 `~/.mineru/config.yaml` | **已删除**，统一写 `.secrets/mineru.json` |

用户如果之前依赖 CLI 的 `~/.mineru/config.yaml`，现在需要在工作台设置页重填一次。这是有意的：两个工作台共用一份 CLI 配置会互相覆盖。

### 3.5.4 写入规则（实现要求）

```text
读取 .secrets/mineru.json
  ├─ 不存在 → 创建 .secrets/ 目录 → 写入 {"token": "..."} → chmod 600
  ├─ 存在但 JSON 解析失败 → 报错并给出路径，不静默覆盖
  └─ 存在且可解析 → 替换 token 键 → chmod 600 → 原子改名
写入方式：先写临时文件 → 设置权限 0600 → 原子改名替换
```

**四条硬要求**：

1. **原子写入**：临时文件 + rename，避免写一半被中断导致 token 损坏。
2. **权限 0600**：新建和覆盖都必须设，不依赖 umask。
3. **解析失败不覆盖**：文件内容坏了要报错，不能当作「空的」重新写——那会静默丢掉用户可能还能手工救回的 Token。
4. **不回显**：见 §4。

### 3.5.5 边界情况

| 情况 | 行为 |
|---|---|
| `.secrets/` 不存在 | 按需创建，随后写文件并设 0600 |
| 文件存在但无 `token` 键 | 视为未配置该来源，落到下一优先级 |
| 文件 JSON 损坏 | 报错并给出路径；不覆盖、不猜测 |
| 磁盘只读 | 保存失败，明确报错，不假装成功 |
| 环境变量 `MINERU_TOKEN` 同时存在 | 界面提示「检测到环境变量 MINERU_TOKEN，文件未配置时它会生效」 |
| 用户以为存在 `~/.mineru/config.yaml` 就够 | 界面必须写明路径是 `.secrets/mineru.json`，不给错误暗示 |

**最后两条尤其重要**：这两处历史上都产生过「填了没用 / 找不到在哪」的困惑。文案要直说路径，不猜。

## 4. 密钥安全（重要）

Token 是凭据，处理规则比普通配置严：

| 规则 | 说明 |
|---|---|
| **存储位置** | `<workbench>/.secrets/mineru.json`（唯一本地密钥文件，见 §3.5），**不写业务资料根**（业务根可能被备份/导出/共享） |
| **不回显** | 保存后只显示后 4 位；不提供查看完整值 |
| **不进日志** | 日志中一律脱敏为 `sk-****`；错误信息不含 token |
| **不进导出** | 备份、诊断包、汇总导出都不含 token |
| **不进 AI 上下文** | 不发送给任何模型 |
| **卸载不删** | 与应用数据同生命周期，卸载插件保留（用户重装无需重填） |
| 明示存储位置 | 设置页说明「Token 保存在本机应用数据目录，不会离开这台设备」 |

**「不会离开这台设备」这句要准确**：token 会随请求发给 MinerU（那是它的用途），但不会被发到其他地方。措辞应写「Token 仅用于向 MinerU 发起解析请求」。

**注意**：token 存在工作台仓目录下的 `.secrets/`，不在业务资料根内，也不在用户主目录的 CLI 配置里。因此：

| 影响 | 说明 |
|---|---|
| 卸载工作台 | token 随仓目录一起保留（`.secrets/` 不被清理脚本触碰） |
| 备份业务资料根 | 不含 token（`.secrets/` 在仓内，与业务根天然隔离） |
| 用户查看/清理 | 直接看 `.secrets/mineru.json`；改完需重启工作台进程才生效 |
| 误提交风险 | `.secrets/` 已在 `.gitignore`；新增仓必须同步补这一条 |

设置页应说明存放路径，让用户知道它在哪里、如何自查。

## 5. 状态矩阵

| 场景 | 表现 |
|---|---|
| 未配置 token + 选云端 | 保存按钮禁用，提示「请先填写 Token」 |
| token 无效（401） | 行内错误：「Token 无效，请确认已复制完整」+ 重新申请链接 |
| 配额用尽（429） | 提示「配额已用尽」，仍可切回仅本地 |
| 校验时无网络 | 提示「无法连接 MinerU，请检查网络」；**不保存** |
| 已配置 | 显示 `sk-····pJqM` + 「校验通过」+ 移除按钮 |
| 关闭云端解析 | 保留 token（下次开启不用重填），状态改为「已配置，未启用」 |
| 用户拒绝隐私告知 | 不启用云端；解析方式保持「仅本地」 |
