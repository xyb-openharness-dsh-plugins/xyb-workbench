## 0. 先看这里：最关键的 6 个待确认问题

> 这三个问题定不下来，后面的方案就只是草稿：

| # | 问题 | 为什么关键 | 我的建议 |
|---|---|---|---|
| Q1 | **谁在用？是家属自己，还是也包含患者本人、或病友志愿者？** | 决定文案语气、是否需要区分"我给家人记"和"我自己记" | 先只做"家属代管"一种，患者本人也用同一个入口，不做多角色权限 |
| Q2 | **一个家庭成员只对应一个病人吗？会不会同时管两个病人（比如配偶和父母都患病）？** | 决定数据模型是"单病人"还是"多档案" | 从第一天就做成"可建多个患者档案"，界面上先只用得到 1 个 |
| Q3 | **病情资料的存放位置：全部放本机，还是允许同步到手机/云端？** | 决定隐私方案和工作量，也决定手机上能不能看 | 第一版只放本机（用户自己选的文件夹），不做云端 |
| Q4 | **AI 解析用哪个模型？用户自带 Key 吗？** | 病历涉及隐私，用云端模型意味着资料会被上传 | 默认走用户已配置的模型，界面上明确提示"资料将发给模型处理"；不做静默上传 |
| Q5 | **临床试验匹配只要"搜到"，还是要打分排序、还要能追踪进展？** | 前者 1 周能做完，后者是大模块 | MVP 只做"按病种+分期+地区搜，能收藏" |
| Q6 | **社区二维码：固定 30+ 个群的图片，还是要按病种/地区动态推荐？** | 决定是"图片墙"还是"有匹配逻辑的模块" | MVP 做图片墙 + 可按病种筛选，不做智能推荐 |

## 1. 需求理解（请确认我是否理解对了）

### 1.1 一句话描述

做一个装在 DSH Desktop 里的**本地优先工作台**，让肿瘤患者的家属能把散落在手机相册、微信收藏、邮箱里的检查报告，整理成一份"问诊前能直接拿给医生看"的规范资料，并顺手解决临床试验匹配、营养、心理、找病友群这几件高频但零散的事。

### 1.2 典型场景（这是真实使用画面，请判断像不像你要的）

**场景 A：问诊前整理（核心场景）**
> 张姐的妈妈确诊胰腺癌三个月，做了两次 CT、四次抽血。文件散在微信里。
> 她把一个叫"妈妈的病"的文件夹指给工作台，里面躺着 3 份 CT 报告 PDF、4 张化验单照片。
> 点"解析"后：
> - 系统认出 4 张化验单里的 CEA 分别是 5.2 → 6.8 → 8.1 → 9.4，画成一条随时间上升的曲线，并标红"较上次上升 16%"
> - 从 CT 文字报告里抽出"胰头占位 3.2cm → 3.8cm""未见肝转移"这类结论，按时间排好
> - 生成一份《病情与治疗汇总》，包含：基本信息、确诊过程、历次影像结论、标志物趋势、用药与副作用、想问医生的问题
> 她把这份汇总打印或截图带去门诊。医生 3 分钟就能看懂这三个月发生了什么。

**场景 B：找临床机会**
> 妈妈化疗耐药后，张姐想知道有没有合适的临床试验。她在工作台里填"胰腺癌 / 一线失败 / 北京或上海"，看到 6 条在招试验，其中 2 条标注"中国有中心"。她收藏了 3 条，每条下面记一句"2026-10-13 已电话问过，需先做基因检测"。

**场景 C：日常照护**
> 化疗后第 5 天，妈妈吃不下饭，体重掉了 2 公斤。张姐打开"营养"页，填一份 10 题的简易评估（吃多少、掉几斤、有没有呕吐），得到一个"中度营养风险"的结论和一份**具体到菜名**的建议（少食多餐、每天蛋白粉 2 勺、这周记录体重）。
> 同一天她情绪很差，在"心理支持"页看到"家属也会撑不住，这是正常的"，做了一份 5 题自评，系统给出放松练习和"什么情况下该找专业帮助"的说明。

**场景 D：找同类人**
> 她在"病友社区"页按"胰腺癌 + 华东"筛出 3 个群二维码，扫码入群。

### 1.3 用户完成一次任务的核心步骤（规范要求的"需求确认闸门"三要素）

| 要素 | 内容 |
|---|---|
| 服务谁 | 肿瘤患者的**主要照护家属**（30–55 岁，会用微信和手机拍照，不太懂电脑技术） |
| 解决什么 | 病情资料散、看不懂、问诊说不清；找不到合适试验；吃什么、怎么撑住、找谁问都靠碰运气 |
| 核心流程 | 建患者档案 → 指定资料文件夹 → AI 解析成规范化汇总 → 看趋势图 → 带着汇总去问诊 → 顺手解决营养/心理/试验/找群 |

## 2. 架构方案对比

### 2.1 先讲一个必须知道的限制

按 DSH Desktop 的《工作台开发规范》：

- **一个 npm 包只能放一个工作台。**
- **工作台的身份 = 它的 GitHub 仓库地址**（`owner/repo`），所以**每个工作台都必须有自己的仓库**，不能几个工作台共用一个包/一个仓库。
- 宿主在侧栏顶部只有一个**模式切换器**：在"原生会话"和"已添加的工作台"之间切换。工作台不能自己造一套入口。
- 一个工作台可以关联很多会话；**一个会话只能属于一个工作台**。

这几条直接决定了方案取舍：拆成 5 个工作台 = 5 个独立仓库 + 用户在侧栏切换器里跳来跳去；合成 1 个工作台 = 1 个仓库 + 内部多 Tab。

### 2.2 三个方案

| 维度 | 方案 A：一个大工作台，内部多 Tab | 方案 B：5 个独立工作台 | 方案 C：混合式（病情主工作台 + 其他独立小工作台） |
|---|---|---|---|
| **长什么样** | 侧栏只有 1 个"肿瘤照护"工作台；面板左侧是 5 个入口：病情管理 / 临床试验 / 营养 / 心理 / 社区 | 侧栏切换器里有 5 个入口，用户自己切 | 侧栏有"病情管理"（主）+ 营养 / 心理 / 社区 / 试验 4 个小工作台 |
| **用户价值** | 最省心：一次进入，数据互相关联（营养评估会引用体重记录，试验匹配会引用病历里的分期） | 每个模块独立干净，但用户要在模式切换器里反复切；跨模块联动做不到 | 折中：核心闭环体验好，小模块不干扰主流程 |
| **开发成本** | 1 个包、1 套构建、1 次安装、1 个仓库。5 个 Tab 内部共享数据层，**最省** | 5 个包 × (包格式 + 构建 + 安装 + 自测清单 + 仓库) ≈ 3–4 倍工作量，且每个都要单独过本地自测 | 1 个大包 + 4 个小包 ≈ 2.5 倍工作量 |
| **可扩展性** | 加第 6 个模块 = 加一个 Tab，不动架构。但单包会越来越大 | 加模块 = 加仓库，边界清楚，但用户侧入口越来越挤 | 核心模块稳定，边缘模块可独立迭代/上架 |
| **会话与上下文隔离** | **弱**：所有会话都属于同一个工作台，一个会话里既有病历上下文又有营养上下文，AI 容易串味 | **强**：每个工作台的会话只装自己的上下文，AI 注意力干净 | 中：核心闭环在一个会话里是**优点**（病情+营养本来就该一起看）；边缘模块独立 |
| **上架/分发难度** | 最低：1 个仓库、1 份验收、1 次投稿 | 最高：5 次投稿、5 次验收 | 中 |
| **风险** | ①单包体量大后构建慢、加载慢；②面板做不好容易变成"功能堆砌"，用户找不到重点；③如果将来想开源某个模块，得从大包里拆出来（要动身份，很麻烦） | ①用户被 5 个入口劝退；②5 个仓库的维护成本对个人开发者偏高；③手机上切换体验差 | ①病情主工作台会成为"什么都往里塞"的垃圾场；②需要提前划清主/小的边界 |

### 2.3 我的推荐：**方案 C（混合式），但第一期按方案 A 落地**

理由，按重要性排序：

1. **病情管理天然是核心，其他四个是"顺手用"的。** 家属 90% 的焦虑集中在"我妈的病情到底怎么样了"。营养/心理/社区是低频、轻量的辅助动作。把核心做成一个厚工作台，辅助做成轻模块，符合真实使用频率。
2. **上下文隔离这条最值得花钱。** 如果病情和临床试验共用一个会话，AI 会把"基因检测结果"和"试验入排标准"混在一段回答里，用户很难读。临床试验、营养、心理各自独立成工作台，各自的会话只装自己的东西，回答质量明显更稳。
3. **但第一期不要真的拆。** 5 个包意味着 5 套构建、5 次本机安装自测、5 个 GitHub 仓库——对刚接触 workbench 开发的你来说，第一次就做这个量级，极可能卡在打包和安装环节上，看不到任何业务效果。
4. **所以路线是：先用 1 个包把"病情管理 + 营养 + 社区"跑通（这三个都属于"围着患者档案转"），AI 验证可行后再把"临床试验"和"心理支持"拆成独立工作台。** 拆分时不影响已用的病情数据——工作台数据是独立文件夹，不是同一份。

**一句话：先 1 个包（方案 A 的形态），但每个模块从第一天就按"将来能独立拆出去"的方式写（独立的目录、独立的配置、不互相直接读对方的内存状态），第 2 期再拆成方案 C。**

### 2.4 不推荐的做法

- ❌ **5 个工作台一起开工**：全是半成品，一个都用不起来。
- ❌ **把聊天窗口替换成业务界面**：规范明确禁止工作台自建聊天界面，必须用宿主提供的会话节点。
- ❌ **让工作台自动在用户主目录建文件夹存病历**：规范明确禁止静默创建目录，必须弹系统目录选择器让用户自己选。这条对医疗数据尤其重要。

## 3. 推荐架构下的信息架构与页面清单

### 3.1 侧栏里长什么样

```
侧栏顶部：[模式切换器] 原生会话 ▾   ...   工作台管理
                    ├─ 原生会话
                    └─ 肿瘤照护        ← 第一期只有这一个
```

第二期会变成：

```
                    ├─ 原生会话
                    ├─ 肿瘤照护        ← 病情管理 + 营养 + 社区
                    ├─ 临床试验
                    └─ 心理支持
```

### 3.2 工作台内部页面（第一期）

| 页面 | 干什么 | 核心流程 |
|---|---|---|
| **① 患者档案**（首页） | 选/建患者；显示当前状态摘要卡 | 进入 → 看到当前患者卡（昵称、病种、确诊日期、最近一次指标）→ 点卡片进入详情；没档案时引导建第一条 |
| **② 资料库** | 指定文件夹、看已收录的文件、手动增删 | 点"选择资料位置"→ 弹系统目录选择器 → 选"妈妈的病"文件夹 → 列出发现的文件 → 用户勾选要解析的 → 点解析 |
| **③ 解析结果** | 展示 AI 抽出来的结构化内容，**允许人工修正** | 解析完 → 左边原文，右边抽取结果 → 用户把认错的字段改掉（比如把"CEA 5.2"误认成"CA125 5.2"）→ 确认入库 |
| **④ 病情汇总**（核心交付物） | 生成规范模板文档，可导出 | 选时间范围 → 生成《病情与治疗汇总》→ 预览 → 导出 PDF/图片/复制文本 |
| **⑤ 指标趋势** | 肿瘤标志物等数值的曲线 | 选指标（CEA / CA199 / CA125 / 白细胞…）→ 看折线 + 变化百分比 → 标出"较上次 ↑16%" |
| **⑥ 影像结论时间线** | CT 文字报告的结论按时间排 | 时间轴形式：2026-07-12 CT：胰头占位 3.2cm，未见肝转移 → 2026-09-20 CT：3.8cm，肝内可疑新发 |
| **⑦ 营养评估** | 简易量表 + 建议 | 填 10 题 → 得到风险等级 → 得到本周行动建议 → 记录体重曲线 |
| **⑧ 病友社区** | 群二维码 | 按病种/地区筛 → 显示二维码图 → 长按保存/扫码 |
| **⑨ 问诊准备** | 把④浓缩成一页"问医生的问题" | 勾选想问的问题 → 生成一张清单 → 打印或存手机 |

### 3.3 统一的文件处理链路（场景 A 的技术画面，用大白话说）

```
用户选的文件夹（本机，用户自己指定）
        ↓
工作台扫描 → 得到文件清单（PDF / 图片 / Word / 文本）
        ↓
用户勾选 → （图片走 OCR，PDF 走文本抽取）
        ↓
AI 按固定模板抽取：日期 / 类型 / 关键结论 / 数值指标
        ↓
【关键：人工确认环节】原文和结果并排显示，用户改错
        ↓
写入本机结构化数据（一份 CSV/JSON，用户能自己打开看）
        ↓
自动更新趋势曲线、时间线、汇总文档
```

**这里有一条产品底线：AI 抽错了必须让人改。** 医疗数据一个数字错了，可能影响医生判断。所以任何 AI 抽取的字段都必须显示原文出处，并且可编辑。

### 3.4 数据放在哪

- 每个工作台有自己独立的根目录，里面就是一个普通文件夹，用户能找到、能备份、能拷走。
- 建议结构（工作台**不会**自动创建，第一次由用户在选择器里确认）：
  - `患者档案/张妈妈/资料原件/` —— 用户放进去的原始文件（工作台不修改）
  - `患者档案/张妈妈/解析结果/` —— 抽取出来的结构化数据
  - `患者档案/张妈妈/导出/` —— 生成的汇总文档
- **卸载工作台不删除任何用户数据。**

## 4. 分期计划

| 期 | 范围 | 交付物 | 预估 |
|---|---|---|---|
| **第 1 期（MVP，验证可行性）** | 患者档案 + 资料库 + 解析结果（人工确认）+ 指标趋势 + 病情汇总导出 | 1 个可安装的工作台包，能在你本机实际用起来，处理真实的一份病历 | 先跑通"选文件夹 → 解析 → 出曲线 → 出汇总"这一条链，其他页先占位 |
| **第 2 期** | 影像结论时间线 + 问诊准备 + 营养评估 | 在同一工作台内加 3 页 | — |
| **第 3 期** | 病友社区（二维码墙） | 加 1 页 | — |
| **第 4 期** | 拆出"临床试验"独立工作台（搜索+收藏+进展记录） | 第 2 个仓库、第 2 个包 | — |
| **第 5 期** | 拆出"心理支持"独立工作台 | 第 3 个仓库、第 3 个包 | — |

**第 1 期为什么选这条链**：它是唯一一条"做完就能立刻用上、且用完有明确产出（一份能带去医院的东西）"的路径。其他模块做完要么是查询、要么是建议，都不产生可交付的成果。

> ⚠️ 注意：第 1 期的"能用起来"有前提条件，见第 7 节。简单说——**做完了不等于装上了**，装上了还要重启一次、登记一次才会出现在侧栏。这三步我会陪你走，但"能不能看到界面"取决于你本机的安装入口是否可用。

## 5. 需要用户确认的问题清单（按优先级）

### 5.1 必须先答（不答没法开工）

1. **Q1 谁用**：只服务家属，还是也要考虑患者本人使用？
2. **Q2 多患者**：会不会同时管理不止一个病人的资料？
3. **Q7 患者档案要填哪些字段**：你说的"规范的病情治疗模板"具体是哪几个字段？（**建议你把现有的那份模板发我，我按它来定抽取规则，不自己编**）
4. **Q8 你手上有什么现成资料**：有没有真实病历样本（可以脱敏）用来测解析效果？是 PDF 为主还是拍的照片为主？照片质量如何？
5. **Q9 分期**：上面第 4 节的第 1 期范围，你认可吗？还是你最想先看到某一块？
6. **Q3 数据位置**：完全本机够用吗？需不需要手机上也能看？

### 5.2 第二阶段要答

7. **Q4 模型**：AI 解析用哪个模型？介意把病历发给云端模型吗？如果介意，要不要走本地模型（速度会慢很多）？
8. **Q5 临床试验**：只要搜到，还是要评分排序 / 追踪申请进度？数据源用 ClinicalTrials.gov 够不够，还是必须包含 ChiCTR 和 CDE？

## 6. 风险与未知项

| 风险 | 说明 | 应对 |
|---|---|---|
| **AI 抽取准确率** | CT 报告措辞千变万化，数值可能被 OCR 认错（5.2 认成 5.7） | 所有抽取结果必须展示原文出处 + 允许人工修改；数值类字段标"待确认"直到用户点过 |

## 7. 开发与验收前置条件（**这一节很重要，请务必看完**）

### 7.1 先说人话：什么叫"做完了"

你可能会以为：做完工作台 → 打开 DSH Desktop 就能看到。

**不是。** 中间有三道关：

```
① 写出包  →  ② 装到本机  →  ③ 重启 + 登记  →  ④ 侧栏出现入口
   （我们做）      （要装）        （必须重启一次）      （才能点开）
```

任何一道过不去，你看到的就是"什么都没有"，而不是"报错"。所以下面把每道关的现状和风险写清楚。

### 7.2 实测结论：**好消息——本地安装这条路是通的**

规范要求"先探测能力，不猜版本号"。我已经实测过你这台机器，记录如下：

| 探测项 | 实测结果 |
|---|---|
| 你本机的 DSH 版本 | `dsh 0.1.0-rc.6` |
| 使用的配置档（profile） | `desktop` |
| 安装插件用的命令 | `dsh plugin add --profile desktop <包>` |
| 该命令支持哪些输入 | 帮助信息里明确列出：`pnpm add <tarball file>`（本地 .tgz 文件）、`pnpm add <dir>`（本地目录）、`pnpm add <name>@<version>`（npm 包） |
| 判定 | ✅ **规范允许"命令明确支持即可安装"，而这里明确支持本地 `.tgz`** |

也就是说：**第 1 期的交付物可以真正装进你的 Desktop，不是只能交一个压缩包。** 这比 v0.1 里的保守估计要好。

### 7.3 但有 3 个坑必须提前知道

**坑 1｜"装上"不等于"启用"。**
装完之后还要把包名登记进配置档的启用清单，工作台才会被加载。这一步容易漏，漏了的症状是：文件都在，重启后侧栏什么都没有。

**坑 2｜必须重启，不能靠刷新页面。**
插件的加载发生在启动阶段，装完必须重启 DSH Desktop。重启前看到的一切"没出现"都正常。

**坑 3｜"配置里能看到"不等于"界面上能用"。**
规范明确写了：用命令导出配置、看到插件层出现，**只能证明配置写对了，不能证明界面加载成功**。真正的验收证据只有两个：
- 在「工作台管理 / 已安装的工作台」里看到条目；
- 从左侧入口真的点开，业务面板真的显示出来。

所以验收时我会要求你配合截图或口述这两步的真实结果，不会拿命令行输出糊弄过去。

### 7.4 还有一件需要你在界面上确认的事

规范要求在 Desktop 界面里的「**工作台管理 / 已安装的工作台**」查找是否存在**本地安装入口**（比如"从文件安装"按钮）。

- 命令行这条路的支持我已经实测确认（7.2）。
- **界面按钮这条路的支持需要你确认**——请打开 Desktop，按 7.5 走一遍，把看到的情况告诉我。
- 如果界面上没有这个入口，**不影响开发**：我改用命令行帮你装，结果一样。

### 7.5 请你现在花 2 分钟做的探测（照抄即可）

1. 打开 DSH Desktop。
2. 找到左侧栏顶部的**模式切换器**（在"原生会话"和"工作台"之间切换的那个下拉）。
3. 点进去，找「**工作台管理**」或「**已安装的工作台**」。
4. 看有没有类似「**从文件安装**」「**安装本地包**」的按钮。
5. 把这个界面上**看到的所有按钮名字**告诉我（或者说"根本没有这个页面"也行）。

### 7.6 万一装不上怎么办（规范的兜底要求）

如果最终确认没有可用的安装方式，或者安装失败，按规范第 9 节，第 1 期的交付物会降级为：

> **一个已经校验过的 `.tgz` 安装包 + 包内容清单 + 校验记录**

此时我会明确告诉你**哪些步骤真的做了、哪些完全没测过**，并且逐项标注为「**未实测**」：

**我不会用"配置写对了"来冒充"跑通了"。** 这是规范明确禁止的，也是对你的数据不负责。

## 8. 插件骨架（给开发的施工清单，用户可跳过）

这一节不写代码，只列**必备字段和文件路径**，作为动手开发的依据。依据是官方《工作台开发规范》第 3 节和你本机实测的版本情况。

### 8.1 包的文件结构

```
<工作台包>/
├── package.json           包清单：名称、版本、入口、dsh 字段（见 8.2）
├── cordis.patch.yml       插件层配置：一条 insert，声明本工作台的数据根目录
├── <服务端入口>.js         exports["."]，提供本机的 /api 接口
├── <客户端入口>.js         exports["./client"]，已构建好的单文件，注册业务面板
├── README.md
└── LICENSE
```

重点：**客户端入口必须是"已经构建好"的单文件**。Desktop 不会替你构建，也不能指望它跑打包命令。

### 8.2 `package.json` 必须字段清单

| 字段 | 要求 | 说明 |
|---|---|---|
| `name` | 必须 | npm 包名。`cordis.patch.yml` 里引用的必须是**包名**，不能写路径 |
| `version` | 必须 | 完整版本号（如 `0.1.0`，不能写 `1.0`） |
| `main` | 必须 | 指向服务端入口 |
| `exports["."]` | 必须 | 同上，服务端入口 |
| `exports["./client"]` | 必须 | 指向已构建的客户端单文件 |
| `exports["./package.json"]` | 建议 | |
| `exports["./cordis.patch.yml"]` | 建议 | |
| `dsh.bundle.patch` | 必须 | 例如指向 `./cordis.patch.yml`。**少了它，包只会被当成普通依赖装进去，插件层不会被激活**——这正是"文件都在但什么都没有"的常见原因 |
| `dsh.client.platform` | 必须 | 固定为 `"web"` |
| `dsh.client.inject` | 必须 | 字符串数组，**必须包含 `dsh-desktop-workbenches`**，否则注册服务拿不到 |
| `peerDependencies` | 建议 | 官方 `@deepseek-ai/*` 包写这里，**不要写进 `dependencies`**，否则会装进第二份宿主代码 |
| `type` | 建议 | `"module"` |

### 8.3 `dsh.client.inject` 需要的 8 个客户端包

工作台骨架依赖以下 8 个宿主客户端包，缺一个都可能在加载或渲染阶段失败：

| # | 包名 | 提供什么 |
|---|---|---|
| 1 | `@deepseek-ai/dsh-client-modules` | 客户端模块加载 |
| 2 | `@deepseek-ai/dsh-client-locale` | 语言/文案 |
| 3 | `@deepseek-ai/dsh-client-ui-conversation` | 会话节点（工作台必须用它，不能自建聊天界面） |
| 4 | `@deepseek-ai/dsh-client-ui-layout` | 布局与面板切换 |
| 5 | `@deepseek-ai/dsh-client-ui-primitives` | 基础控件 |
| 6 | `@deepseek-ai/dsh-client-ui-sidebar` | 侧栏插槽 |
| 7 | `@deepseek-ai/dsh-client-ui-settings-general` | 通用设置 |
| 8 | `@deepseek-ai/dsh-client-ui-workspace` | 工作区 |

> 另需在注入列表里加上工作台服务本身：`dsh-desktop-workbenches`。

### 8.4 `cordis.patch.yml` 的写法要求

- 文件内容是**一个 YAML 数组**，第一条是 `insert`，在 `insert` 里放本工作台的插件条目。
- 条目里 `id` 是插件条目标识、`name` 必须是 **npm 包名**、`config.root` 用 `!!js dshHomePath('xxx')` 声明**本工作台独立的根目录**（工作台之间数据不串）。
- ⚠️ 文件**不能为空、也不能只有注释**，否则启动会失败。实在没内容要写 `[]`。
- ⚠️ 如果 `id` 和已有条目重名，会**整体替换对方的 config，而不是合并**——所以 `id` 要起得足够独特。

### 8.5 服务端与客户端入口的形态

| | 必须提供 | 关键约束 |
|---|---|---|
| **服务端入口** | 插件名、注入清单（至少含 `connection`）、配置校验规则、`apply` 函数 | 配置校验**必须**用 Schemastery 的 schema 对象；本机接口统一放在自己的前缀下（`/api/<工作台 id>/`）；判断"这个会话属于哪个工作台"要用宿主暴露的只读查询服务，不要自己猜 |
| **客户端入口** | 一个已构建的单文件模块；`apply` 函数 + `inject` 清单 | 通过 `window.__ModuleLoader__.load({ id: '<包名>', factory })` 注册；`factory` 里 `require` 只能拿共享基线（React、Cordis 等）和已加载插件；调用 `ctx.desktopWorkbenches.register(...)` 时必须提供 `title`、业务组件、**规范的 GitHub repository URL**；新包**不要**填 `register({ id })`；注册返回的注销函数要交给 `ctx.effect` 管理 |

### 8.6 界面边界（做的时候不能越线）

- **不得自建聊天界面**，必须把宿主提供的会话节点放进业务布局。
- `customFrame` 不得越过宿主容器的裁剪边界，不得覆盖左侧会话栏。
- 无会话、无工作区时业务面板必须**立即可用**；浏览/创建业务档案不得以"已有会话"为前提。
- **不得在默认位置、用户主目录或推测路径静默创建文件夹**；需要保存文件时必须调用宿主的目录选择器。用户取消时不能留下空目录、空项目、工作区、会话或绑定。
- 顶部模式切换器和管理入口是宿主的，工作台不得复制、遮挡或替换。

完整仓库已克隆到：`/tmp/dsh-desktop-src`（开发时参照里面的包结构）

## 附录：给开发看的规范要点（用户可跳过）

- 工作台 = 1 个 npm 包 + 1 个 DSH 插件 bundle + 1 个 Desktop 业务面板；**一个包只能放一个工作台**。
- 客户端 `ctx.desktopWorkbenches.register({ title, repository, description, ... }, BusinessPanel)` 注册；`repository` 必须是规范的 GitHub URL，工作台身份由此解析为 `owner/repo`。
- `package.json` 必须声明 `dsh.bundle.patch`、`dsh.client.platform = "web"`、`dsh.client.inject` 含 `dsh-desktop-workbenches`、`exports["./client"]`。
- `cordis.patch.yml` 里 `root: !!js dshHomePath('xxx')` 指定本工作台独立数据目录。
- 宿主提供唯一的模式切换器和"工作台管理"入口，工作台不得复制/遮挡。
- 无会话/无工作区时业务面板必须立即可用；浏览档案不得以已有会话为前提。
- **不得在默认位置/主目录/推测路径静默创建文件夹**；需保存文件时必须调用宿主目录选择器。
- 不得自建聊天界面，必须使用宿主提供的 `conversation` 节点。
- 本机自测通过即可自用；上架市场是另一套验收规范，可选。
- **本机安装能力已实测**（v0.2 补充）：`dsh 0.1.0-rc.6` + profile `desktop`，`dsh plugin add --profile desktop <spec>` 的帮助信息明确支持 `pnpm add <tarball file>` / `<dir>` / `<name>@<version>`。安装后需把包名加入 profile 的 `dsh.profile.bundles` 才会被激活，并重启 Harness。`dump-config` 只能证明配置，不能替代 UI 加载证据。
- 官方市场安装接口（`/api/desktop-workbenches/market-install`）**只接受公开市场目录里的 identity，且安装源被硬编码为 registry**，无法用于本地 `.tgz`。本地包只能走 CLI 或 Desktop 插件安装界面这条路，不要试图绕过。
