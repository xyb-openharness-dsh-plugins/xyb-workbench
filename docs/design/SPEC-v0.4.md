## 0. v3 工程实施顺序

本节将产品分期落实为实际开发与验证顺序。每一阶段完成后记录真实证据和未验证项；未通过前不得把后续依赖能力写成已可用。

| 顺序 | 阶段 | 产物与完成条件 |
|---:|---|---|
| 1 | Schema Freeze v1 | 冻结公共试验库边界、Agent 任务与会话字段、治疗周期/预约/提醒关系、确认状态与值状态语义；`0001` 首次用于真实资料后不再改写，后续仅新增 `0002+` 迁移。 |
| 2 | SQLite 服务端最小闭环 | 用户选择业务根；迁移、事务、原件目录、仓储层与备份可用；完成“文档导入 → 候选字段 → 用户确认 → 指标趋势/看板同步”。 |
| 3 | 命令与读模型 | 定义并实现版本化写入命令和读模型；优先看板、病情核对、指标趋势、一图秀、营养读模型。客户端不直连 SQLite。 |
| 4 | DSH 工作台包 | 建立独立 npm/DSH 插件包，完成 `package.json` dsh 声明、`cordis.patch.yml`、Schemastery 服务端入口、构建后的 web 客户端和 `desktopWorkbenches.register()`。 |
| 5 | v3 界面落地 | 以 v3 原型为交互与视觉验收基线，将七个 Tab 改为真实 React 页面，先接读模型再接写入命令；不复制宿主导航或聊天界面。 |
| 6 | 离线试验检索 | 先接入 ChiCTR SQLite 与 XYB CDE JSON，完成来源状态、版本、检索、收藏、规则初筛与快照；其他来源逐个独立验收。 |
| 7 | Agent 协作 | 核实目标 DSH Desktop 的公开会话、归属与草稿接口；“给我建议”提交可编辑页面摘要，结果进入候选收件箱，确认后才写入业务库。 |
| 8 | 导出、订阅与跨平台 | 完成 HTML/PDF/JPEG 导出、试验订阅、周期任务恢复，再分别验证 macOS arm64、macOS x64 与 Windows x64。 |

### 0.1 DSH 接入硬要求

- 包必须含完整 SemVer、服务端 `exports["."]`、客户端 `exports["./client"]`、`dsh.bundle.patch`、`dsh.client.platform="web"`，且 `dsh.client.inject` 包含 `dsh-desktop-workbenches`。
- 服务端使用自己的 `/api/xyb-workbench/` 路径，SQLite、文件、子进程和密钥只在服务端处理。
- 客户端注册一个工作台业务面板；业务区不遮挡宿主侧栏、市场、设置和模式切换，原生 conversation 节点由宿主提供。
- 无会话时可浏览、选择患者、录入和查看本机资料；只有发起 Agent 动作时才创建或恢复本工作台归属会话。
- 首次需创建业务资料根时调用宿主目录选择器；取消不创建目录、工作区、会话或空项目。
- 最终从 `pnpm pack` 的 `.tgz` 安装，按工作台开发规范完成“已安装列表、左侧入口、实际打开和业务操作”本机自测。

### 0.2 目标版本现场核实项

工作台包格式与责任边界已清晰。开发前或进入对应阶段时，必须在目标安装的 DSH Desktop 核实目录选择、创建/恢复工作台归属会话、向原生草稿追加上下文、技能/MCP 注册与卸载的公开 API 签名；不得依赖私有 DOM 或猜测接口。

## 1. 定位变更：v0.3 → v0.4

### 1.1 变更原因

v0.3 把产品定位为**病情资料整理工具**：整理资料、核对抽取、准备问诊，临床试验作为附加的离线检索能力。总览页是「下一步做什么」的任务清单。

本轮用户明确的新定位是**病人状态总控台**：不仅要整理资料，还要把整理结果转成多维度的**结构化评估**，并据此做**临床匹配初筛**和**日常照护管理**。总览页从任务清单升级为**全局状态看板**。

这不是补几个 Tab，而是产品定位改动，因此本稿重排范围与信息架构。

### 1.2 定位对照

| 维度 | v0.3 | v0.4 |
|---|---|---|
| 产品隐喻 | 桌上的一份清楚的病情资料 | 病人的状态总控台 + 一份清楚的病情资料 |
| 首页 | 下一步任务清单 | **全局看板**：一屏掌握病人综合状态 |
| 病情整理终点 | 汇总/导出 | 汇总/导出 **+ 病情分析评估**（结构化结论） |
| 临床试验 | 检索 + 收藏 | 检索 + 收藏 **+ 结构化匹配初筛 + 渠道配置** |
| 照护面 | 移入阶段 4，首期不显示 | **一期建导航与占位，二期实现 7 类管理** |
| 数据粒度 | 文档 → 候选事实 → 观察值 | 增加：基因/病理结构化、治疗线数、并发症状态、毒性分级、营养、心理、管路 |

### 1.3 保留不变的部分

v0.3 中以下设计经验证仍然成立，v0.4 继续沿用，不重复论证：

- **证据链原则**：每条事实能回到原始资料与页码/原文；未核对值不进入正式数据。
- **本机优先**：患者资料留在本机；在线模型调用前给简短提示。
- **可解释、不越界**：不输出诊断、疗效判断、入组保证；区分「未知」与「正常」。
- **离线可用**：无 Key、无网络、无会话也能用核心功能。
- **不修改宿主**：不复制/遮挡模式切换、会话栏、工作台管理入口；不自建聊天界面。
- **目录选择**：保存文件前必须调用宿主目录选择器，不静默创建目录。

## 2. 已确认决策

本轮通过提问确认了三个关键决策，作为本稿的既定前提。

| 决策点 | 结论 | 影响 |
|---|---|---|
| **首期范围** | 重排为「**全局看板 + 一期三模块 + 营养/心理/全程管理**」，共 7 个一级 Tab | 一期聚焦病情整理、病情一图秀、临床匹配三条链，看板做全局聚合 |
| **匹配度算法** | **规则库 + 人工确认**，AI 只做抽取建议 | 匹配结果可解释、可追溯、可复现；不做纯语义黑箱评分 |
| **看板维度** | 8 个维度全上：体能、治疗/线数、可匹配临床、营养、心理、并发症、毒性、（总体关注项） | 看板是完整状态面板，不是只做导航 |
| **匹配度输出** | 三档：**已满足 / 可能冲突 / 无法判定** | 不输出「符合入组」结论，最终判断交给医生 |

### 2.1 未决项（实现前需确认）

| 事项 | 状态 | 阻塞什么 |
|---|---|---|
| 患者病情/治疗汇总模板 | **未提供（唯一硬阻塞）** | 决定 AI 抽取字段与看板数据模型 |
| 1–3 份脱敏真实报告样例（CT + 化验单 + 病理） | 未提供 | 决定抽取器与核对界面的字段设计 |
| 线上模型/OCR 能力的实际接缝 | 未核实 | 决定 AI 辅助是「建议候选」还是「不可用」 |
| 入排规则库的初始条目来源 | 未定 | 见 MATCHING-SPEC §4 |
| 目标平台与架构 | 未定 | 先完成 macOS arm64 开发机验收 |
| 通用搜索 skill 与数据库渠道的实际接口 | 未核实 | 见 MATCHING-SPEC §5 渠道配置 |

## 3. 一期范围：全局看板 + 两个模块

```text
小胰宝工作台
├─ 全局看板（默认首页）           ← 一期，见 DASHBOARD-SPEC.md
│
├─ 模块一：病情整理                ← 一期核心
│  ├─ 智能病历整理
│  ├─ 病情分析评估               ← v0.4 新增
│  └─ 主要指标可视化
│
├─ 动态病情一图秀                  ← 一期核心，单独 Tab，见 TIMELINE-SPEC.md
│  ├─ 指标趋势图（多指标 + 标注 + 关键点）
│  ├─ 用药时间轴（与趋势图时间对齐）
│  └─ CSV 导入 / 导出（迁移与可携带）
│
├─ 模块二：临床搜索与匹配初筛       ← 一期核心
│  ├─ 患者入组条件档案
│  │  ├─ 个人基因突变记录 / 组化病理
│  │  ├─ 并发症状态
│  │  └─ 治疗线数与方案管理        ← 与病情整理、一图秀同源

│
├─ 营养管理                      ← 一期一级 Tab，见 CARE-MANAGEMENT-SPEC.md
│  ├─ 当前状态（BMI / 体重变化 / PG-SGA）

│

│  ├─ 情绪自评（DT / GAD-7 / PHQ-9 / HADS）
│  ├─ 心理缓解（小馨宝社群、自助方法）
│  ├─ 安宁疗护（机构查询、生前预嘱）
│  └─ 哀伤管理（公益支持机构、哀伤常识）
│
└─ 全程管理                      ← 原「照护管理」更名收窄
   ├─ 毒性管理（CIPN / 皮疹等，CTCAE 分级）
   ├─ 并发症管理（出血 / 胆道梗阻 / 肠梗阻 / 感染）
   ├─ 带管管理（PTCD / 手术置管）
```

**一级 Tab 共 7 个**：`1 看板 | 2 病情整理 | 3 病情一图秀 | 4 临床匹配 | 5 营养管理 | 6 心理支持 | 7 全程管理`。营养与心理从原照护管理中提升为一级，理由见 [CARE-MANAGEMENT-SPEC §1.2](./CARE-MANAGEMENT-SPEC.md)。

### 3.2 一期能力表

| 能力 | 纳入内容 | 完成边界 |
|---|---|---|
| **全局看板** | 8 维度状态卡、需关注项列表、模块跳转 | 每格有明确口径与状态分级；缺口显示「未评估」而非默认正常 |
| **智能病历整理** | 文件导入、文本提取（本地优先 / MinerU 兜底）、候选抽取、**多文件核对**、确认入库 | 见 EXTRACTION-SPEC；候选值不自动确认；字段规格见 CASE-TEMPLATE-SPEC |
| **病情分析评估** | 基于已确认事实生成结构化评估（分期、治疗史、器官功能、体能） | 只归纳已确认事实，不补写、不推断疗效；AI 润色可关闭 |
| **主要指标可视化** | 已确认指标的趋势、数据表、参考范围、来源定位 | 沿用 v0.3 §7.1 规则：不插值、不合并不同单位、不自动解释升降 |
| **动态病情一图秀** | 指标趋势图 + 用药时间轴 + 时间轴标注；默认读本机数据；CSV 导入导出 | 见 TIMELINE-SPEC；不改写数据、不自动解读峰谷、单位不一致不连线 |
| **基因/病理记录** | 结构化记录基因突变、IHC 标志物、检测方法与标本、报告日期 | IHC 需支持六种结果类型；「未检测」与「阴性」必须区分 |
| **并发症状态** | 记录主要并发症及其状态（活动/既往/无/未知） | 供匹配规则与全程管理共用 |
| **治疗线数与方案** | 一线/二线/三线…方案、起止、疗效评价、终止原因、药物明细 | **与病情整理、一图秀同一数据源**；线数允许人工调整 |
| **渠道配置** | 检索渠道的启用、状态、覆盖范围、更新 | 见 MATCHING-SPEC §5；未就绪渠道不冒充可用 |
| **匹配度分析** | 逐条入排标准命中情况、三档汇总、依据与来源 | 不输出入组结论；未知项如实列出 |
| **营养管理** | BMI、体重变化、PG-SGA 自评、能量目标与实际差距、胰酶替代记录 | 只做记录与差距提示，不给补充剂或食谱推荐 |
| **心理支持** | 情绪量表自评与趋势、小馨宝社群入口、安宁疗护机构查询、哀伤支持资源 | **心理数据不发送给任何模型**；不诊断、不解读分数；危机提示常驻 |
| **全程管理** | 毒性（CTCAE）、并发症、带管、血管通路四项的记录与查看 | 一期不做自动提醒推送；红色只表示客观异常 |

### 3.3 明确的非目标（一期不做）

- 不做诊断、疗效判断、用药建议、预后预测。
- 不做「符合入组条件」的肯定结论或自动报名。
- 不做多个病人的横向对比或队列分析。
- 不做机构管理、多角色协作、云同步。
- 全程管理、营养管理、心理支持**一期全部进导航并实现查看与记录**；不做自动提醒推送、不做心理诊断、不做营养处方。

### 4.2 病情整理 → 临床匹配的数据同步

治疗线数与方案管理**必须与病情整理打通**，这是用户明确要求，也是最容易做成两套数据的地方。设计规则：

| 规则 | 说明 |
|---|---|
| 单一事实来源 | 治疗记录只存一份（`TreatmentLine` 实体），病情整理的「治疗经过」、病情一图秀的「用药时间轴」、临床匹配的「治疗线数」是同一数据的三个视图 |
| 双向可见 | 在病情整理里编辑方案，临床匹配的入组档案与一图秀立即反映；反之亦然 |
| 派生而非复制 | 匹配规则读取的是 `TreatmentLine` 的规范化字段（药物通用名、线数、起止日期、终止原因），不额外维护一份「匹配专用表」 |
| 药物名称归一 | 记录原名 + 标准化通用名。匹配「用过伊立替康」这类规则依赖通用名归一，归一表可维护、可追溯 |
| 冲突处理 | 同一线数出现多条冲突记录时，标注冲突并要求用户确认，不静默取一条 |

字段定义见 §6.1 的 `TreatmentLine`。

### 4.3 三处治疗数据的显示差异

同一份 `TreatmentLine`，三处显示不同、来源相同：

| 视图 | 显示重点 | 允许编辑 |
|---|---|---|
| 病情整理 · 病情评估 | 时间线 + 疗效 + 终止原因 | ✅ 完整编辑 |
| 病情一图秀 · 用药时间轴 | 起止色块 + 短标签，与指标趋势时间对齐 | ❌ 只读，提供跳转到编辑 |
| 临床匹配 · 入组档案 | 线数序号 + 药物通用名（供规则匹配） | ✅ 编辑药物明细与线数 |

一图秀只读是有意的：图表是**看**的地方，编辑容易误操作，且会打断时间对齐的视觉连续性。

### 4.3 宿主职责边界

沿用 v0.3 §4.2，不重复。补充两点：

- 看板属于业务内容，不是宿主组件；不占用或复刻宿主任何入口。
- 匹配分析结果不得以弹窗、角标或颜色暗示「推荐入组」。

## 5. 关键流程

### 5.1 首次进入（无患者）

1. 打开看板页，显示空状态：「建立患者档案」+「先浏览试验资料」两个入口。
2. 浏览试验不要求先建档、不创建目录或会话。
3. 建档先填昵称，再选资料根目录；取消不留下空档案或目录。
4. 无模型配置也可建档、收录资料、手工录入、浏览试验；AI 相关按钮说明需要模型，但不阻断其他功能。

### 5.2 病情整理主链（沿用 v0.3，增加评估节点）

```text
导入资料 → 本地文本提取 → (可选)AI 候选抽取 → 人工核对 → 确认入库
   → 指标趋势 / 病情评估 / 病情汇总
   → （治疗记录同步到）临床匹配 · 入组档案
```

评估节点规则：

- 病情评估只使用**已确认事实**，未核对候选不参与。
- 评估结论每条附来源；没有资料的部分显示「暂无已确认资料」。
- AI 润色必须引用已有确认记录，不新增诊断、用药或疗效判断；可整体关闭。
- 评估结果可重新生成，不覆盖用户已编辑的历史版本。

### 5.3 临床匹配主链（详见 MATCHING-SPEC.md）

```text
维护入组档案（基因/病理、并发症、治疗线数）
   → 配置并检查检索渠道
   → 检索/筛选试验
   → 选择试验 → 抽取入排条件 → 人工确认规则
   → 逐条判定：已满足 / 可能冲突 / 无法判定
   → 汇总展示 + 依据 + 来源
   → 收藏并记录跟进状态
```

### 5.4 失败状态（增量）

沿用 v0.3 §5.5 全部条目。新增：

| 场景 | 用户看到 | 行为 |
|---|---|---|
| 入组档案字段缺失 | 匹配结果该条标「无法判定」，并指出缺哪个字段 | 不当作「已满足」；提供补录入口 |
| 入排规则未确认 | 该条标「待确认规则」，不计入三档统计 | 提供规则确认入口，不自动判定 |
| 药物名称无法归一 | 标「名称待确认」，不自动匹配既往用药规则 | 提供选择/新增归一入口 |
| 渠道未就绪 | 「该渠道未启用/未就绪」，其余渠道结果照常显示 | 不把缺渠道显示成「没有试验」 |
| 看板某维度无数据 | 显示「未评估」及补录入口 | 不能显示为「正常」或绿色 |

## 6. 数据模型

### 6.1 新增与扩展实体

v0.3 §6.1 的实体（`Patient`、`Document`、`Evidence`、`ExtractionRun`、`CandidateFact`、`Observation`、`ClinicalFact`、`Summary`、`TrialRecord`、`TrialSnapshot`、`TrialBookmark`、`TrialNote`、`SessionBinding`、`Job`、`DatasetGeneration`）全部保留。新增：

| 实体 | 关键字段与规则 |
|---|---|
| `GenomicAlteration` | `alterationId`、`patientId`、基因名、变异类型（突变/融合/扩增/缺失）、变异描述（如 exon 2 突变）、临床意义、检测方法（NGS/IHC/PCR）、标本类型、报告日期、证据、确认状态；无结果须区分「未检测」与「检测阴性」 |
| `IHC marker` → 归入 `GenomicAlteration`，用 `assayType='IHC'` | 标志物名（B7-H3、CLDN18.2、PD-L1、HER2、MSI/dMMR 等）、结果（阳性/阴性/分数）、判读标准、报告日期、来源 |
| `ComorbidityStatus` | `comorbidityId`、`patientId`、并发症类型、状态（活动/既往/无/未知）、严重程度、记录日期、来源；供匹配与照护共用 |
| `TreatmentLine` | `lineId`、`patientId`、**线数序号**、方案名、药物列表（原名 + 标准化通用名）、给药方式、起止日期、周期数、疗效评价、终止原因（进展/毒性/患者意愿/完成）、证据；**病情整理、一图秀、临床匹配共用此实体**；线数允许人工调整 |
| `TimelineAnnotation` | `annotationId`、`patientId`、锚定日期、标注文本、偏移量、来源；用于一图秀的竖线标注（如「pectCT 情况 1」）；见 TIMELINE-SPEC §3.3 |
| `TimelineDataset` | 一图秀的三份 CSV 快照元信息：导入来源、导入时间、行数、修正记录（如尾引号修正）、导出记录；用于解释「图上这条数据从哪来」 |
| `ToxicityRecord` | `toxicityId`、`patientId`、毒性类型、CTCAE 分级、发生日期、关联治疗线、处理、转归；一期只做数据结构预留，二期界面 |
| `NutritionAssessment` | `assessmentId`、`patientId`、评估日期、身高、体重、BMI、体重变化趋势、能量摄入估计、能量目标、差值；一期预留 |
| `PsychAssessment` | `assessmentId`、`patientId`、评估日期、量表类型与得分、分级、建议；一期预留 |
| `CatheterRecord` | `catheterId`、`patientId`、类型（PTCD/手术置管/Port/PICC）、置入日期、位置、状态、并发症、维护记录；一期预留 |
| `TrialEligibilityRule` | `ruleId`、来源试验键、来源文本片段、规则类型、结构化条件、确认状态（待确认/已确认/已排除）、确认人时间、规则版本；见 MATCHING-SPEC §3 |
| `MatchAssessment` | `assessmentId`、`patientId`、试验键、规则集版本、逐条判定、三档汇总、评估时间、档案快照版本；可复现的历史记录 |
| `DataChannel` | `channelId`、名称、类型（skill/database）、启用状态、就绪状态、覆盖范围、最后检查时间、最后成功时间、失败原因；见 MATCHING-SPEC §5 |
| `DashboardSnapshot` | `snapshotId`、`patientId`、生成时间、各维度取值与分级、数据版本引用；看板展示与历史对比用 |

`GenomicAlteration` 依据真实模版补充子字段（`vaf`、`tmb`、`tumorCellPct`、`resultType`、`intensity`、`assay`、`rawText`、`normalizedBy`），`ClinicalFact` 补充（`histology`、`tumorSize`、`invasion`、`vi`、`pni`、`margin`、`labNo`）。完整定义见 [CASE-TEMPLATE-SPEC.md](./CASE-TEMPLATE-SPEC.md) §6。

### 6.2 数据同步与一致性

- `TreatmentLine` 是唯一权威来源，病情评估、匹配规则、看板都从它派生。
- `MatchAssessment` 记录生成时的档案 revision；档案变更后旧评估标「档案已更新，需重新评估」，不静默重算。
- `DashboardSnapshot` 不持久化冗余事实，只存引用与生成时取值，用于解释「当时为什么显示这个状态」。
- 所有时间使用含时区 ISO 8601；无法确认时显式 `unknown`。可编辑实体带 `revision`。

### 6.3 存储布局

沿用 v0.3 §6.2 三类目录划分与业务根布局，新增实体归入同一数据库，不新增目录层级。

持久层选型、启动口令、字段级加密与原件策略已冻结，详见 [STORAGE-SPEC.md](./STORAGE-SPEC.md)。要点：采用 Node 内置 `node:sqlite`（本机实测可用，零原生依赖）；**不做整库加密**，改用启动口令（访问控制语义，忘记可恢复）；**病历原件不进数据库**，作为普通文件保存在业务根下。

## 7. 界面与交互原则

详细见 [UI-DESIGN.md](./UI-DESIGN.md)。本稿只锁原则：

1. **看板是状态面板，不是警报器**。用中性色表达「需关注」，不用满屏红色制造恐慌；不使用「危险」「恶化」等未经确认的判断词。
2. **缺口显式**。任何没有数据的维度显示「未评估」，不能默认正常。
3. **每个结论有出处**。看板、评估、匹配的每个判断都能点回原始资料或规则依据。
4. **三档不合并**。匹配结果的「无法判定」是独立档位，不能并入「已满足」或「冲突」。
5. **一期不放假按钮**。尚未实现的子页显示说明，不渲染可点击但无功能的控件；已实现页只展示真实可用的记录与查看。
6. **心理维度不用红绿灯**。全看板唯一例外，理由见 PSYCH-CARE-SPEC §8。
6. **响应式按业务容器宽度**，不按窗口宽度；窄容器下看板降为单列。

## 9. 验收要点

完整责任矩阵见 [INTEGRATION-DESIGN.md](./INTEGRATION-DESIGN.md) §7.3。本稿新增业务验收场景：

| 场景 | 必须观察到 |
|---|---|
| 看板首次无数据 | 8 维度均显示「未评估」及补录入口，不显示为正常 |
| 看板数据口径 | 每格状态可点开看到口径说明与数据来源 |
| 治疗线数三处同步 | 在病情整理改方案，临床匹配入组档案与一图秀时间轴都立即反映，无第二份数据 |
| 药物名称归一 | 记录了「伊立替康」后，含该药排除条件的试验匹配识别为「可能冲突」 |
| 匹配三档完整性 | 缺基因结果时该条为「无法判定」，不落入「已满足」 |
| 档案变更后重评 | 旧评估标「需重新评估」，不静默沿用旧结论 |
| 渠道未就绪 | 未启用渠道显示自身状态，其他渠道结果照常 |
| 一图秀默认可用 | 打开即显示该患者图表，不需要先手动选三个 CSV |
| 一图秀单位安全 | 同名指标不同单位不被连成一条线 |
| 一图秀不改写数据 | 导入带格式问题的 CSV（如日期尾引号）时修正并留记录，不改写用户原始文件 |
| 一图秀峰谷无解读 | 图上不出现「方案有效」「指标好转」等自动结论 |
| 营养管理 | BMI 从指标记录自动派生，不要求重复录入；只显示差距不给处方 |
| 心理支持 | 危机提示在四个子页都常驻；量表分级用官方分界；心理数据不进 AI 上下文 |
| 全程管理 | 四个子页可查看与记录；无假按钮、无自动推送 |
| 窄容器 | 看板降为单列，一图秀图表可读、无横向溢出、无单字竖排 |
| 宿主边界 | 不遮挡模式切换/会话栏/工作台管理；无会话时业务面板可用 |
