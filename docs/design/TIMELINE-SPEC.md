## 1. 结论先说：能实现，而且是最容易做对的一块

你问「这个项目能否在看板中实现」。分三层回答：

| 层面 | 结论 | 依据 |
|---|---|---|
| **数据层** | ✅ 完全可行，且风险最低 | 三个 CSV 结构极简（共 4 列主键 + 2 列辅助），可直接进本机存储，也可无损导出回 CSV |
| **图表层** | ✅ 可行 | 现实现用 ECharts + PapaParse，两者已本地 vendored（`js/echarts.min.js` 1.0MB、`js/papaparse.min.js` 20KB），不依赖 CDN |
| **看板集成** | ⚠️ 不作为看板内嵌，**单独一个 Tab** | 见 §2。理由不是技术限制，是信息密度与使用场景冲突 |

**唯一真正的技术风险不在这个页面**，而在宿主是否允许工作台加载 ECharts 这样的浏览器端库、以及图表交互在 customFrame 内的尺寸响应。这属于 INTEGRATION-DESIGN 的宿主接缝验证范围，不阻塞设计。

## 2. 为什么单独一个 Tab，而不是塞进看板

你说「这个页面也比较特殊，可以单独配置一个 tab」——我同意，而且有具体理由。

### 2.1 与看板的设计原则冲突

| 看板原则 | 一图秀的实际形态 | 冲突 |
|---|---|---|
| 一屏掌握状态 | 需要横向滚动 2022–2030 时间轴 | 一图秀是「细看」，看板是「速览」 |
| 不做医学判断 | 用药时间轴与指标峰谷对比**天然引导因果推断** | 用户会自己看出「换方案后指标降了」 |
| 中性色、不铺大数字 | 图表需要颜色区分多条线、多个方案色块 | 视觉语言不同 |

这不是说一图秀不好——它恰恰是**病友最想要的功能**。但它和看板服务的是不同的认知任务：看板回答「现在怎么样」，一图秀回答「这一年是怎么走过来的」。

### 2.2 导航位置

推荐：**一级 Tab 第 3 位，命名「病情一图秀」**

```text
看板 | 病情整理 | 病情一图秀 | 临床匹配 | 照护管理
```

放在「病情整理」之后，因为它是病情数据的**可视化视图**，与整理同源；放在「临床匹配」之前，因为匹配需要先有完整的病情时间线。

## 3. 数据模型

现有三个 CSV 的字段与语义：

### 3.1 `data.csv` — 指标记录

```csv
testTime,indicatorName,indicatorValue
2023-11-01,AST,28
2023-11-01,ALP,76
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `testTime` | 日期 `YYYY-MM-DD` | 采样/报告日期 |
| `indicatorName` | 文本 | 指标名（中文或英文缩写） |
| `indicatorValue` | 数值 | 指标值 |

**现状**：665 条数据，长表格式（一行一个指标值），这是正确的设计——新增指标不需要改表结构。

**映射到工作台模型**：直接对应 `Observation`（见 SPEC-v0.4 §6.1）。`indicatorName` 走指标别名归一，`indicatorValue` + 单位 + 参考范围进 `Observation`。

**需要补的字段**（现有 CSV 没有但工作台必须有）：

| 补什么 | 为什么 |
|---|---|
| `unit` | 不同单位不能直接连线（SPEC §7.1）；现有数据靠约定，工作台必须显式 |
| `refRange` | 判断「高于参考范围」需要它；缺失时看板相关维度显示「未评估」 |
| `sourceDocumentId` | 证据链要求每条值能回到原件 |
| `confirmStatus` | 未核对值不进趋势（沿用 v0.3 主链规则） |

**关键决定**：工作台内部模型比 CSV 丰富，但**CSV 导入导出必须保持兼容**。导出时缺失字段留空，不写占位值。

### 3.2 `medication.csv` — 用药方案

```csv
PATIENT_ID,START_DATE,END_DATE,DRUG_NAME,TAG
1,2023-10-10,2023-11-29,手术期间,
2,2023-12-01,2024-05-01,Gx,GX
3,2024-11-02,2025-01-01,FOLFIRINOX,四药
```

| 字段 | 说明 |
|---|---|
| `PATIENT_ID` | 单患者工具里是自增序号；工作台改为真实 `patientId` |
| `START_DATE` / `END_DATE` | 方案起止；`END_DATE` 空 = 进行中 |
| `DRUG_NAME` | 方案名（如 `AG 方案1`、`FOLFIRINOX`） |
| `TAG` | 时间轴色块上显示的短标签（如 `四药`、`GX`） |

**映射到工作台模型**：对应 `TreatmentLine`（SPEC-v0.4 §6.1）。这正是我在 SPEC 里强调的「治疗线数与病情整理单一事实来源」——一图秀的用药时间轴、病情评估的治疗经过、临床匹配的入组档案，**必须是同一份数据**。

**这里有个必须解决的冲突**：现有 `medication.csv` 的 `DRUG_NAME` 是**方案名**，不是药物列表。而匹配规则需要的是**具体药物通用名**（「用过伊立替康」）。

| 处理 | 说明 |
|---|---|
| 方案名保留 | 用于时间轴显示与用户认知（`mFOLFIRINOX` 比四个药名好认） |
| 药物列表必填 | 每个方案记录所含药物，才能支持既往用药规则 |
| 归一 | 药物通用名归一（MATCHING-SPEC §2.4） |
| 导入兼容 | 只有方案名时，标记「药物明细待补充」，匹配时相关规则判「无法判定」，**不能**当作「未用过」 |

### 3.3 `remarksline_update.csv` — 时间轴标注

```csv
REMARKS_DATE,REMARKS,OFFSETX,OFFSETY
2023-11-09',pectCT，情况1,0,0
2024-10-23',pectCT，情况2,0,10
```

| 字段 | 说明 |
|---|---|
| `REMARKS_DATE` | 标注锚定的日期（画成竖线） |
| `REMARKS` | 标注文本（如 `pectCT，情况1`、`普美显情况4`） |
| `OFFSETX` / `OFFSETY` | 文本相对锚点的像素偏移 |

**现状问题**：`REMARKS_DATE` 值带一个多余的尾引号（`2023-11-09'`），是生成脚本的 bug。工作台导入时必须容忍并修正，同时记录「已修正」，不能静默改写或直接报错拒绝。

**映射**：新增 `TimelineAnnotation` 实体（SPEC-v0.4 §6.1 需补）。

**`OFFSETX/OFFSETY` 的取舍**：这是像素级手调值，依赖具体图表尺寸。工作台的图表宽度是响应式的，固定像素偏移在窄容器下会错位。

| 方案 | 评价 |
|---|---|
| 保留像素偏移 | 与现工具一致，但窄容器错位 |
| 改为相对锚点自动布局 | 更稳，但与现有 CSV 不兼容 |
| **保留字段 + 自动避让** | **推荐**：导入时保留原值作为初始位置，渲染时检测重叠并自动避让；导出时写回用户调整后的值 |

## 4. 页面设计

### 4.1 布局

```text
┌─ 病情一图秀 ────────────────────────────────────────┐
│ 时间范围 2022 — 2030  [重置]      显示控制            │
├──────────────────────────────────────┬──────────────┤
│                                      │ 时间筛选      │
│   指标趋势图                          │ 2022 — 2030  │
│   （多指标折线 + 标注竖线 + 关键点）    │              │
│                                      │ 显示控制      │
│                                      │ ☑ 关键点      │
│                                      │ ☐ 变化率      │
├──────────────────────────────────────┤              │
│                                      │ 选择指标      │
│   用药时间轴                          │ [搜索框]      │
│   （方案色块 + 图例）                  │ ☑ ALP        │
│                                      │ ☐ ALT        │
│                                      │ ☐ CA199      │
└──────────────────────────────────────┴──────────────┘
```

### 4.2 数据来源（关键改进）

现有工具用**文件选择器**加载三个 CSV。工作台里应该：

| 方式 | 说明 |
|---|---|
| **默认读本机数据** | 从工作台存储直接读该患者的 `Observation` / `TreatmentLine` / `TimelineAnnotation`，打开即可用 |
| **CSV 导入** | 保留文件导入，作为迁移旧数据与批量补录的入口 |
| **CSV 导出** | 随时导出回三个同格式 CSV，保证数据可携带、不被锁死 |

这一条很重要：**看板里的一图秀应该是「打开就有」，不是「先选三个文件」**。文件选择是迁移手段，不是日常操作。

### 4.3 必须补的安全性设计

现有工具作为个人自用脚本没问题，但进工作台需要补：

| 补什么 | 为什么 |
|---|---|
| **不自动解读峰谷** | 图上一眼能看出「换方案后指标降了」，但这不等于「方案有效」。图下方需常驻说明，与 v0.3 §7.1 规则一致 |
| **单位不一致不连线** | 现有实现按 `indicatorName` 分组，同名不同单位会被连成一条线，这是错误 |
| **缺测不插值** | 沿用 §7.1 |
| **参考范围分段显示** | 同一指标参考范围随检测方法变化时，不能只画一条线 |
| **未确认值区分** | 候选值可显示为浅色点并标「尚未计入」，但不能参与趋势线 |
| **导出前确认** | 导出 CSV 含患者数据，需说明文件去向 |

### 4.4 保留的好设计

现有工具这几处做得对，应当保留：

- **长表数据格式**：新增指标不改结构，这是可扩展性的关键。
- **关键点与变化率开关**：让用户自己决定信息密度。
- **年份范围筛选 + 底部缩放条**：长时间跨度必需。
- **用药时间轴与指标图上下对齐**：这是这个工具的核心价值——**时间对齐让用户自己看出关联**。
- **图例即筛选器**（点击图例可切换方案色块）。

## 5. 与看板的关系

两者共享同一份数据，但展现不同：

| | 看板 | 一图秀 |
|---|---|---|
| 问题 | 现在怎么样？ | 这一年是怎么走过来的？ |
| 时间跨度 | 最近一次 + 变化趋势 | 全病程 |
| 粒度 | 状态级别 | 每个数据点 |
| 交互 | 点开看依据 | 缩放、筛选、悬停看值 |
| 数据 | 聚合后的分级 | 原始已确认记录 |

**看板的「需关注项」可以跳转到一图秀的对应时间点**，这是两者最有价值的连接：看板说「体重 1 个月下降 6.2%」，点进去看到体重曲线在这一段的实际走势。
