# 小胰宝 v3 按页面成组实现与验收方案

日期：2026-10-14  
用途：调整当前开发节奏，避免边写一个小控件边反复做局部验证，同时防止 React 实现偏离 v3 原型。

## 结论

可以先按完整页面或组织单元集中实现，再按 Tab 和共享能力做成组测试。推荐节奏是：**先完成一个完整业务页面的结构、交互、读写链路，再运行该页面的单元与集成检查；页面稳定后做跨 Tab 回归。**

不建议把七个 Tab 全部一次性写完后才第一次验证。那会把布局、状态、API 和数据模型问题堆到一起，定位成本更高。也不需要每改一段样式或每加一个控件就单独跑一轮测试。

## 原型一致性原则

`prototype-v3.html` 是高精度原型，也是当前产品界面的默认实现基准。除非有明确且可说明的原因，正式工作台应与它在**布局、信息层级、组件形态、文案、交互路径和动效反馈**上保持高度一致。开发不能只沿用配色和标题后自行重组页面，也不能以“功能大致都有”代替原型一致性。

允许偏离原型的情况限定为：

- DSH Desktop 宿主 API、窗口或导航规则确实不支持原型中的实现方式；
- 接入真实数据后，原型演示数据或静态内容会造成事实失真；
- 无障碍、键盘操作、减少动态效果或小屏适配需要补充行为；
- 已确认的业务规则、安全边界或数据约束要求调整。

发生偏离时，必须在 parity matrix 中记录原型项、偏离内容、具体原因、采用的替代方案和验收方式；应尽量保留原型呈现意图。没有记录原因的偏离视为实现缺口，应修复到与原型一致。

## 现状评估：原型与实现没有按功能清单逐项映射

当前 `prototype-v3.html` 是高精度交互原型，`lib/client.js` 是独立重建的 React 页面。React 页面复用了部分色彩和页面名称，但尚未按原型组件结构及交互移植，导致功能和布局出现实质差异；这些差异没有已记录的宿主或业务限制作为依据，应按实现缺口处理。

| 区域 | v3 原型表现 | 当前 React 实现 | 评估 |
| --- | --- | --- | --- |
| 病情一图秀 | 指标选择控件、趋势图、治疗时间线、记录来源说明；后续需求还要求多指标联动和治疗节点对齐 | 分类指标卡、看板概览内容、分开的治疗事件列表 | 不是同一个信息结构。没有时间轴图，也没有多选指标和治疗事件叠加 |
| 指标看板 | 最近结果、变化提示、按分类分组；已确认的需求规定点击卡片后以动效显示最近 5 次趋势 | 前后内容直接替换，静态 SVG sparkline | 有切换状态，但没有翻面动画；日期与数值密度、重点层级也不同 |
| 指标数据 | 卡片应显示最近检测值、与前次差异和记录日期；趋势必须来自已确认记录 | 使用后端观察值与历史接口，基本数据链路已有 | 数据来源方向正确，但展示和交互尚未达到设计验收 |
| 共享结构 | 原型以一套页面壳、卡片、分类、弹窗和导航组织 | React 页面重新组合了壳和模块，部分内容临时复用看板概览 | 需要以原型结构为基线，避免模块互相塞入导致内容重复或缺失 |

### 病情一图秀应实现的页面闭环

1. 指标搜索/筛选与多选；选择项在图例和图表中同步体现。
2. 同一时间轴显示所选指标的已确认记录；单位不兼容或单位变化时明确分轴或暂停连线。
3. 治疗、化疗、检查等事件作为时间节点/区间叠加，能筛选显示。
4. 点击数据点可查看数值、日期、单位、来源报告及确认状态。
5. 提供空状态、单条记录状态、缺失数据状态、大字模式和窄窗口布局。
6. 只做病程回顾和复诊沟通准备，不生成疾病进展或疗效诊断。

### 指标卡应实现的页面闭环

1. 按肿瘤标志物、血常规、肝功能、感染与炎症、肾功能、代谢与营养等分类展示，组间留白。
2. 正面显示最近一次结果、日期、单位、较前次变化值及上升/下降/持平提示。
3. 点击后完成明确的卡片翻转动效，背面展示最近 5 次已确认记录的可读趋势和日期。
4. 再次点击可返回；键盘操作和减少动态效果设置均可用。
5. 不将颜色或箭头解释为病情诊断；缺少两次记录、单位不一致时显示明确说明。

## 推荐的开发分组

### 第 0 组：基线与映射

- 将原型每个 Tab 的区域、控件、交互、状态列成 parity matrix。
- 每一项绑定 React 组件、数据模型/API、验收方式和完成状态。
- 将明确的后续需求标在对应原型项旁，区分“原型已有”和“后续增加”，避免误把静态演示内容当成完整业务需求。
- 先复用现有 SQLite 与服务端读写链路；不因界面重做而另建一份前端事实源。

### 第 1 组：共享界面和图表能力

- 页面壳、标题区、分类标题、空/加载/错误状态、建议按钮、大字模式。
- 可复用的指标卡正反面和交互动效。
- 可复用的时间轴/折线图、图例、多选、数据点详情和可访问性支持。
- 共享组件完成后做一次组件级检查，不对每个视觉微调单独跑完整测试。

### 第 2 组：逐 Tab 形成完整垂直闭环

建议顺序：看板 → 病情一图秀 → 病情整理 → 营养管理 → 全程管理 → 临床匹配 → 心理支持。看板作为工作台首页，先按原型恢复层级、8 个维度、提醒与体重趋势；再处理一图秀和指标卡动态。其余页面均按同一高精度一致性原则重构，不只局部补缺。

每个 Tab 在一个实现批次中完成：页面结构、主要交互、读模型、写入/确认链路、加载/空/错误状态、相关提示文案。首页批次包含周期卡和可操作的两周日历（逐日选择、列表、新增、修改、完成/取消）；日历复用 `appointment` 单一事实源。随后一次性运行该 Tab 的组件测试、API/存储集成测试和人工验收清单，再进入下一个 Tab。

每个页面都先完成原型内容映射，再进入 React 实现。病情一图秀与看板能同时验证观察值历史、治疗事件、来源定位、图表与患者切换，是检验“单一事实源”是否成立的关键页面。

### 第 3 组：跨页面回归

- 同一条观察值新增/确认后，看板提醒、指标卡、时间轴三处读数一致。
- 新增或修正治疗事件后，看板周期计划、病情一图秀和全程管理一致。
- 首页日历新增/改期/完成/取消后，患者隔离正确；计划事件不自动转写为已确认的治疗事实。
- 患者切换后，当前页面数据、历史记录、图表选择和弹窗全部切换到同一患者。
- 迁移、导入、失败恢复、文件路径和本地资料根做服务端集成检查。
- DSH 宿主安装、入口、患者切换、Agent 草稿交接最后做端到端验收。

## 测试节奏

| 时点 | 检查范围 | 目的 |
| --- | --- | --- |
| 共享组件成组完成 | 组件/状态测试 | 固定卡片翻转、图表坐标、数据格式化等共用行为 |
| 一个 Tab 的功能批次完成 | Tab 组件测试 + 对应 API/存储集成测试 | 确认页面内完整流程可用，不只验证静态渲染 |
| 每 2–3 个关联 Tab 完成 | 关联页面回归 | 检查共同读模型和共享组件没有漂移 |
| 里程碑结束 | 全套自动化 + DSH 本机手动清单 | 核实安装包和宿主交互 |

不要在每次改 CSS、文案或单个表单字段后都重复执行整套回归。若某次改动影响共享读模型、迁移、患者隔离、权限或文件路径，则应立即跑对应的窄范围检查。

## 逐页验收矩阵模板

每个 Tab 用同一张表追踪，不以“页面看起来差不多”作为完成条件：

| 原型/需求项 | 页面组件 | 数据来源/API | 状态与交互 | 测试/人工检查 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 例如：指标多选 | TimelineMetricPicker | 已确认 observation history | 增/减选择后图例和曲线同步 | 多选、空值、患者切换、键盘操作 | 待实现 |

完成定义：该 Tab 所有确认项有落点；真实业务数据来自统一存储；主要交互可操作；空/错误状态清楚；自动检查通过；页面清单逐项人工验收。未支持项必须写出宿主或数据边界及替代方案，不用静态原型数据伪装已实现。

## 实施建议

接下来先停止给当前页面零散加控件。先为首页和其余六个 Tab 建立 parity matrix，逐项标记原型结构、信息层级、交互和动效；按页面完整重构，先看板，再做“病情一图秀 + 指标卡翻转”，随后处理其余页面并成组验证。这样既减少反复测试，也能尽早纠正目前最明显的原型偏差。任何偏离都要先写明具体依据与替代实现。
