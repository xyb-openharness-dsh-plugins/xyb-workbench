# 迁移与版本兼容操作手册

日期：2026-10-13 · 适用：`node:sqlite` 本机库（`xyb.db`）
配套：`0001_initial.sql`（初始建表）、`migrate.mjs`（迁移执行器）
原则：**先备份 → 事务内执行 → 校验 → checkpoint**；失败整体回滚，不留下半成品。

---

## 1. 日常操作

```bash
# 查看状态（只读，不写入）
node migrate.mjs --db <业务根>/xyb.db --dir <schema 目录> --check

# 执行迁移（自动先备份）
node migrate.mjs --db <业务根>/xyb.db --dir <schema 目录> --backup-dir <业务根>/backups
```

执行器行为：

| 环节 | 行为 |
|---|---|
| 版本识别 | 文件名前四位数字 = `PRAGMA user_version`，两者不一致直接报错 |
| 幂等 | 已应用版本按 SHA-256 校验；重复运行不重复执行 |
| 防篡改 | 已应用版本的 SQL 被改动则拒绝继续 |
| 事务 | 每个迁移在 `BEGIN/COMMIT` 内执行；失败 `ROLLBACK` |
| 约束 | 每次连接执行 `PRAGMA foreign_keys = ON` |
| 收尾 | `foreign_key_check` + `integrity_check` + `wal_checkpoint(TRUNCATE)` |

---

## 2. 备份硬要求

- `xyb.db`、`xyb.db-wal`、`xyb.db-shm` 与 `patients/**/documents/` 必须**同根、同时备份**。
- 备份前先 `PRAGMA journal_mode = WAL` 再 `PRAGMA wal_checkpoint(TRUNCATE)`，避免复制到未合并内容。
- 不允许出现「有库无原件」或「有原件无库」。
- 执行器已按此实现；手工备份必须复现同样顺序。

---

## 3. 新增迁移的写法

1. 文件名 `NNNN_简述.sql`，`NNNN` 为四位递增版本号。
2. 首行写 `PRAGMA user_version = NNNN;`（执行器会剥离该语句后执行）。
3. 一个迁移只做一类变更；建表、加列、加索引分开写，便于回滚定位。
4. 注释说明**为什么**要改，以及旧版本客户端会看到什么。
5. 不要写 `DROP COLUMN`、`DROP TABLE`、语义改写；收缩列到「延后收缩」阶段。

### 兼容模式：扩展 → 转换 → 切换 → 延后收缩

| 阶段 | 做法 | 允许旧客户端 |
|---|---|---|
| 扩展 | 加新表 / 新列（带默认值或可空）/ 新索引 / 新字典 | 是 |
| 转换 | 双读或双写，旧路径仍可用 | 是 |
| 切换 | 写新路径，旧路径降级为只读或兼容视图 | 视契约 |
| 延后收缩 | 旧列停止写入；跨大版本后才删除 | 否（需先确认无旧版本在用） |

## 4. 版本兼容测试清单

桌面应用可能长期离线，必须分别验证两个方向：

| 场景 | 期望 |
|---|---|
| 新程序读旧库 | 迁移自动执行；旧数据不丢；校验与完整性检查通过 |
| 旧程序遇新库 | 明确报错并提示升级，不得静默读到半升级数据 |
| 备份恢复 | 恢复后数据库与原件均可读，数量与校验值一致 |
| 中断重放 | 迁移中途断电/退出后重新运行，结果一致且不重复应用 |
| 已应用版本被改动 | 拒绝继续，不覆盖已有记录 |
| 三类数据 | 旧数据、待确认数据、纯手工录入数据分别验证 |

---

## 5. 变更判定

| 想要改的东西 | 动哪一层 |
|---|---|
| 布局、排序、Tab、文案 | 界面，不产生迁移 |
| v3 以简化形态展示 v2 能力 | 界面，领域字段保留 |
| 新增要筛选/排序/画趋势的字段 | 加列并建索引 |
| 真实病历出现模型存不下的字段 | 改领域模型 |
| 枚举新增取值 | 先扩展字典；必要时新增迁移放宽 CHECK，并保留旧值可读 |

## 6. 已知未决

- FTS5 中文 trigram 分词未实测，未纳入初始迁移；验证后单独加迁移。
- 字段级加密列清单未定；加密只改写入层，不改列类型。
- 读模型旧契约保留时长与下线流程待定；库升级与契约下线不是同一步骤。
- `node:sqlite` 为实验性 API；Node 主版本升级后须重跑本手册全部用例。
